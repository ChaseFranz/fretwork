## Design

**1. The fork does not score drums itself.** It waits for upstream's `calc_metrics` path, its `CALIBRATION_GROUP['drums']`, its `DRUMS_REMAP_BINS` and its `Methodology.md` table, and takes them with the usual `git fetch upstream && git merge upstream/main`. Rejected: fitting bins here against `diff_drums` (the data is in the cache and the fit is a morning's work), because it would make the site's "engine unchanged" sentence false, put a calibration table in the fork that upstream's own later table would fight in every merge, and cross the line CLAUDE.md draws around shared tooling. The measured distributions above go to upstream as a comment on their branch, nothing more.

**2. One flat stream per entry, built at the fork's boundary, in the fork's file.** `difficulty.flat_notes(notes)` returns a `{'time_ms', 'lanes'}` stream for every shape: the cache's own object when `'time_ms' in notes`, and when `'hand_mask' in notes` a union of hand and kick timestamps with hand bits 0 to 4 and kick shifted to bits 5 and 6 (bit 5 kick, bit 6 2x kick), masks OR-ed where the two streams share a timestamp. It keys on shape, never on the instrument name, because CLAUDE.md keeps instrument names inside `instruments.py` and section 10's `notes_hash` makes the same decision the same way. Bits 5 and 6 are the reserved, unused bits CLAUDE.md names, and drums has no open note (`SUPPORTS_OPEN_NOTES['drums'] = False`, `instruments.py:152`), so bit 7 stays free too; `density.fret_var` then counts a kick as a lane change with no code of its own. `difficulty.flatten_entry(entry)` returns a copy of an `entries_by_code` entry with `notes` and `expert_notes` flat and the originals under `raw_notes` and `expert_raw_notes`. It is called at the fork's three sites, `entry_difficulty`, `GraphRenderer.lookup` (`web/graph.py:41-43`) and `render.py`'s loop (`render.py:58-59`), and nowhere in upstream's files: `functions/cache.py` and `analyze.py` stay byte-identical to upstream, so the next merge of the file that carries upstream's drums work cannot conflict with fork code. If upstream's D consumes a merged stream of its own, `flat_notes` delegates to upstream's function and the fork's merge is deleted, so D and the graph agree exactly, as they do for guitar. If upstream scores the two streams separately, the fork's merge stays as the display stream only, and `entry_difficulty` passes `raw_notes` to upstream's calculation whenever `not scorable(raw_notes)`. Rejected: teaching `window_arrays` a drums branch, because five consumers would each need to know which shape they hold and it is upstream's file; flattening inside `cache.entries_by_code` or before `calc_metrics` in analyze's loop, because both are upstream's files and the loop is the one upstream is about to rewrite (section 00 rejected `entries_by_code` for the same reason); a hands-only stream, because kick is 26% of the timestamps and the busiest drum charts are kick charts; keying on `instrument == 'drums'`, because the shape is the fact and the name is `instruments.py`'s.

**3. One curve per drums chart, whatever upstream draws.** The site's graph explains one number, and section 06's renderer, hover readout and compare overlay are all written against one `win`/`var` pair. So the curve JSON for a drums code is the v1 shape from section 05, computed from the flat stream. If upstream's `calc_curves` returns one pair for drums, that is the pair; if it returns two (hands and kick), the fork sums them window for window, padding the shorter grid with zeros, into one pair. Rejected: a two-line hands-and-kick graph on the site, because it doubles every path in section 06 for 3,756 charts to explain a split the number itself does not show; if upstream's `plot.py` draws drums as two streams, the PNG it makes is still what `GraphRenderer.render` (`web/graph.py:46-58`) mirrors from `render.py:58-70`, which only matters until section 06 retires the PNGs. The OG image is a guitar chart either way.

**4. The skip goes; the predicate stays.** `analyze.py:126` goes with upstream's commit, not the fork's (see step 1 for the one case where the fork removes it). Section 00's `difficulty.scorable` and `SCORED_KEYS` stay exactly as they are: `flatten_entry` runs before `scorable` sees the entry, so the predicate remains the shape check for any stream that is not `{'time_ms', 'lanes'}` (a future vocals stream, or any fork call site that reads the cache without flattening), and only its outcome for drums changes. `test_scorable_rejects_drums_shape` still passes on the raw pair; `test_lookup_returns_none_for_drums_code` flips to asserting an entry with `time_ms`. Rejected: deleting the guard because it "can never fire", because it can, and section 00 says outright "Section 11 will remove the skip and must not remove the predicate".

## Data and interfaces

**`functions/difficulty.py`**, the fork's file, two names this section owns beside section 00's `scorable`:

- `flat_notes(notes) -> {'time_ms': float64 ndarray sorted, 'lanes': uint8 ndarray}`. Identity when `'time_ms' in notes`. When `'hand_mask' in notes`: `t = concat(hand.time_ms, kick.time_ms)`, `l = concat(hand.lanes, kick.lanes << 5)`, stable sort by `t`, `np.unique` on `t`, `np.bitwise_or.at` the masks that share a timestamp. Measured on `76023951XD` Expert: 977 hand + 410 kick timestamps become 1,015. Delegates to upstream's merge function when one exists (a one-line body then). Any other shape raises `TypeError` naming the keys it saw.
- `flatten_entry(entry) -> entry`: a shallow copy of an `entries_by_code` entry with `notes = flat_notes(entry['notes'])`, `expert_notes = flat_notes(entry['expert_notes'])` (or `None`), `raw_notes = entry['notes']`, `expert_raw_notes = entry['expert_notes']`. Idempotent: on an already-flat entry it returns a copy with the same objects. `entry_difficulty` calls it first, then `scorable`, so a raw entry from `entries_by_code` and a flattened one from `lookup` give the same block. ## Risks and gotchas

- **The tiers may read high on day one.** Under the shared `BASE_D`/`LN_INC`, a merged stream puts 23% of Expert drums at CalcTier 6+ against 8% by `diff_drums`. Whether upstream fits drums constants, or a hands-weighted stream, is upstream's call; the site publishes what the engine says under the beta note, which already says calibration is moving. Do not "fix" it here.
- **The stunt cutoff.** The rating branch excludes `CalcTier >= 10` (`elo:SkillRating.md:24`); the merged measurement puts 4 drums charts there. The rating never touches `web/`, and drums ratings are out of scope, but the cutoff is a named parameter for this reason.
- **Two shapes for one key.** `entry['notes']` from `cache.entries_by_code` still means two different things by instrument, and that is upstream's file. Any consumer of an entry in the fork must take it through `flatten_entry`; `entry_difficulty`, `lookup` and `render.py` are the three, and `bundle.fingerprint`, `fingerprint_curves` and `curves_bytes` all receive `lookup`'s entry. The grep in step 4 should also cover `hand_mask` and return only `cache.py`, the two parsers, `build.py` and `difficulty.py`. The fixture's drums songs are what catch a new consumer that forgets.
- **The render header reads `diff -1` until the backup column is filled.** `load_backup_diffs` turns `''` into `'-1'` (`ini_updater.py:133`), `plot.py:88-89` prefers it to `meta`, and `repr(original_diff)` sits inside `bundle.fingerprint`, so a backfill done after the first drums publish re-renders 3,756 PNGs and re-uploads about 685 MB a second time. Step 3 fills the column first for that reason. After section 06 the canvas prints the row's `Difficulty` (from `meta`) and only `render.py`'s PNGs are affected.
- **`NaN` in the formula.** `remap_diff` returns `None` and `calc_tier` raises on `NaN` (`formula.py:68-83`); `aNPS + medNPS > 0` whenever notes exist, and the flat stream always has notes because `build.py:78-83` drops a level only when both sub-streams are empty. An upstream drums variant that averages two streams could produce it, and there is no assertion for it in the fork: watch for the analyze summary's `Rows written` total exceeding the sum of the level matrix, which is the only visible sign of a skipped row (`analyze.py` counts `skipped` at `:157` but does not print it).
- **Cymbals and lanes are invisible.** Pro-drums markers (`.chart` `N 66-68` mark cymbals; `.mid` pitches 110-112 mark toms, the convention is inverted between the formats) and the `pro_drums`/`five_lane_drums` ini keys (dropped at `ini_parser.py:96-106`) are not parsed, so D cannot tell a cymbal from a tom or a four-pad chart from a five-pad one. The explainer sentence says so. Lane 5 appears in 1,941 of 3,756 levels, all from `.mid`, so this is common, not an edge case.
- **`README.md:66` is upstream's sentence.** It arrives reworded in some future merge; rewording it here creates a conflict in a file both sides touch. Prefer taking upstream's wording if it lands first, and keep the fork's edit to the sentences upstream does not have.
- **Publish and deploy cost.** Before section 06, 3,756 PNGs is about 685 MB uploaded once and 7.5 minutes of render; after it, 3,756 curve files at about 3.9 KB each. Deploy after 06 if the order allows; if not, it is a one-off.
- **Level chips on an all-levels sheet.** Every drums song has all four levels, so the default Expert + Official view (`main.js:58-59`) shows 880 of the 939 songs; clearing both chips shows 3,756. Expected, not a bug.
- **The leaderboard link.** The userscript's `INSTRUMENT` map and section 13's `LEADERBOARD_INSTRUMENT` both stop at `Keys`; without the `Drums` entry a drums row's link is silently wrong or absent. The `?q=&code=` form and the modal `aria-label` are unaffected.
