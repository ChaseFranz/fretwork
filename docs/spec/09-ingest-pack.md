# 09. Pack ingestion tool

**Status:** Ready after 03 and 04

**Effort:** M, dominated by the source handling (three archive kinds, a download with a cap, the wrapper-folder and name rules, and the pre-flight refusals that keep a bad input from touching `songs/`), not by the pipeline calls, which already exist.

**Depends on:** 00 (the backup CSV header drift: the first song this tool adds is exactly what appends a 7-field row under the 6-field header, so the fix must land first), 03 (owns `packs.toml` and `functions/packs.py`; this tool calls `packs.load` and `packs.append_pack` and writes no TOML itself), 04 (the `tests/` tree, `tests/fixture.py` and `tests/pipeline_test.py`, which the ingest stage and `tests/test_ingest.py` join)

## Goal

One command takes a pack from wherever it is (a `.zip`, `.rar` or `.7z` on disk, a folder, or a direct download URL), puts a chart-only copy under `songs/<name>/`, records it in `packs.toml` through section 03's `append_pack`, rebuilds and re-analyses the library, and prints what changed against the previous cache. README section 7 becomes ingest, publish, deploy. The tool stops at analyze: publishing and deploying stay the two commands they are today, printed at the end of the summary.

## Why

- Adding a pack today is six manual steps spread across README 7 and a paragraph about `tools/sanitize_songs.py` (`README.md:228`, `:238-259`): copy the folder in, sanitise with `--apply`, build, read the summary, find the errors CSV, analyze. Every one of those has a way to go quietly wrong (wrong `--search-path`, forgetting `--apply`, a build in the wrong header), and the checks the README asks for ("the song count moved", "the errors CSV did not jump") are done by eye.
- Song-pack requests arrive as GitHub issues with a link (`.github/ISSUE_TEMPLATE/song-pack.yml:21-28`); the tool's input is that link or the archive it points at, and its output is the `packs.toml` entry section 03's changelog page lists, so the request-to-changelog path has no manual bookkeeping in it.
- The library on the dev box was assembled by hand and shows it: 24 of the 26 packs under `songs/` carry a wrapper folder that repeats the pack name (`songs/Rock Band 1/Rock Band 1/<song>/`), because that is how the archives unpacked; only `Guitar Hero III (Individual Songs)` and `practice` do not. The tool strips that wrapper, so packs ingested from here on have one shape.
- Audio never enters the library (CLAUDE.md, the issue form, the hosting design). Making the sanitizer a step the tool always runs before a pack lands in `songs/`, rather than a command to remember afterwards, is what makes that a property rather than a habit.

## Current state

**What a pack goes through today.** `README.md:228` says to run `python tools/sanitize_songs.py songs --apply` by hand; `README.md:238-259` then runs `build.py --search-path songs --header Local` and `analyze.py --header Local` and lists the checks to make between them. Nothing records which packs are in the library or when they arrived: pack identity in the data is only the `song.ini` `icon` mapped through `sources/*.txt` into the `Release` column (`parsers/ini_parser.py:108-114`), and the folder name under `songs/` reaches the cache only inside `song_path`. Section 03 adds the registry; this section adds the tool that feeds it.

**The sanitizer** (`tools/sanitize_songs.py`) is a 175-line script whose logic lives entirely in `main()` (`:84-171`) behind `argparse` (`:85-91`). `classify()` (`:50-59`) keeps `KEEP = {'song.ini', 'notes.chart', 'notes.mid'}` by lower-cased name, removes the audio, image, video and scratch extensions in `REMOVE` (`:35-42`) only from folders that hold a song.ini or a notes file (`scan()`, `:62-74`, decides `in_song` per directory), drops `desktop.ini`, `Thumbs.db`, `.DS_Store` and `:Zone.Identifier` streams anywhere (`:46-47`), and leaves everything else alone and listed. It `sys.exit`s twice: a root that is not a directory (`:94-95`) and a root with no song folder (`:117-118`). It has no callable entry point, so a caller today has to `subprocess` it.

**Build and analyze.** `build.build_cache(search_path, header)` (`build.py:43-170`) walks `song.ini` with `rglob` (`parsers/ini_parser.py:137`) and the note files with two process pools (`parsers/mid_parser.py:324-338`, `parsers/chart_parser.py:286-300`, 31 workers on the 32-core dev box). All three `rglob`s are case-sensitive on Linux (verified on 3.12.3: a folder holding `Song.ini` is not found), and the parse-error rows they append carry `str(file)` as the walk produced it (`ini_parser.py:142`, `chart_parser.py:274`, `mid_parser.py:313`), which is relative when `--search-path` was, while `EmptyStream` rows carry the resolved absolute `song_path` (`build.py:88-91`). Build writes `caches/<header>_cache_<MMDDYYYY-HHMM>.pkl` (`functions/timestamp.py:13,27-32`) and the errors CSV only when there were errors (`build.py:159-165`), with two separate `timestamp()` calls (`:145`, `:160`) and a 105 MB pickle written between them, so the two stamps can differ across a minute boundary. It always appends new songs to `caches/<header>_BackupData.csv` (`build.py:111-124`), and prints the per-instrument, per-level matrix through `instruments.level_matrix` (`build.py:156-157`, `functions/instruments.py:184-200`). There is no incremental build: a new pack means re-parsing every song. `analyze.analyze(header=...)` (`analyze.py:95`) takes the newest cache by mtime (`functions/timestamp.py:46-55`), reuses its stamp for the xlsx (`analyze.py:174-175`), skips drums (`analyze.py:126`), and honours `config.DIFF_WRITE_MODE` when no `--diff-mode` is passed (`analyze.py:97`), which is the one way an automated run could write to `song.ini`. `config.OUTPUT_DIRS` (`config.py:128-133`) are relative strings resolved against the working directory, which is how section 04 keeps CI output out of the repo.

## Design

**Where the tool runs from.** `REPO = Path(__file__).resolve().parent.parent`; `sys.path.insert(0, str(REPO))` before any project import, because `python tools/ingest_pack.py` puts `tools/` at `sys.path[0]`, not the repo root. Every path argument (`SOURCE`, `--library`, `--packs`) is resolved against the current working directory, as the five entry points resolve theirs; the working files go under `Path(config.OUTPUT_DIRS['cache']) / 'ingest'` resolved the same way; and the two subprocesses inherit the tool's cwd and are addressed by absolute path (`[sys.executable, str(REPO / 'build.py'), ...]`). So the tool is run from the directory where `caches/` and `metrics/` should land: the repo root by hand, `<work>/ingest/` in CI (section 04's pattern). Rejected: pinning the subprocesses' `cwd` to the repo root, because a CI run would then write caches into the checkout and the tool's own `caches/ingest/` would be in a different place from the caches it goes looking for.

**Pre-flight: every refusal that can be decided without touching anything is decided first**, in this order, before a byte is fetched or a directory created: `--name` shape (one path component: no `/` or `\`, not `.` or `..`, not starting with `.`, not empty); `config.DIFF_WRITE_MODE is None` (`analyze()` would honour it, `analyze.py:97`, and this tool never writes a `song.ini`); `--source` is `''` or starts with `http://` or `https://` (the rule `packs.load()` enforces, so the failure is the tool's sentence, not a `PacksError` after the rename); the `SOURCE` kind is accepted; `unrar` or `7z`/`7zz` is on PATH when the suffix needs one; a URL host is not in `NOT_DIRECT`; then the registry: `packs.load(args.packs)` (a `PacksError` is `refused: <packs>: <message>`), and the folder and name checks below. Only then does the run start. Rejected: a confirmation prompt, because the script runs unattended in CI and `--replace` is the confirmation.

**`--replace` is defined against the registry and the library together.** Four states, decided in pre-flight from `packs.load(args.packs).by_folder` and `(library / name).is_dir()`:

| registered | folder exists | without `--replace` | with `--replace` |
|---|---|---|---|
| no | no | ingest, append the entry | same |
| no | yes | `refused: <library>/<name>/ exists (pass --replace to replace it)` | remove the folder, ingest, append |
| yes | yes | `refused: <name> is already in packs.toml (pass --replace to re-download it)` | remove, ingest, keep the entry |
| yes | no | same refusal (the entry says the folder should be there) | ingest, keep the entry |

An entry describes the folder, and a re-download is the same pack, so with `--replace` an existing entry is left alone and the summary says `packs.toml  entry kept (already registered)`; "the source changed" is a hand edit of the file, never a re-ingest. A `--name` equal to a registered `name` whose `folder` differs is a refusal in every state, since `packs.load()` requires both unique. The one realistic use of `--replace`, re-downloading a pack that is already listed, is therefore the case that completes. Rejected: `--replace` deleting and re-adding the entry, because that would move `added` and rewrite a hand-edited `notes`.

**One script, one source argument.** `tools/ingest_pack.py SOURCE --name NAME [--source URL] [--header Local] ...`. `SOURCE` is one of: a path ending `.zip`, `.rar` or `.7z`; a directory; an `http(s)` URL whose path (or `Content-Disposition` filename) ends in one of those suffixes. Anything else is refused with a sentence saying what is accepted. Rejected: guessing the kind from magic bytes, because a URL has to be judged before it is downloaded, and a suffix rule is one the operator can predict.

**Archives.** `.zip` through `zipfile`, member by member, so the tool can repair names and skip what it must. Before extracting, the sum of `ZipInfo.file_size` over the members is compared with `--max-bytes` and the archive is refused when it exceeds it, with the sum in the message; the download cap alone says nothing about what a zip inflates to. `.rar` and `.7z` only through an external tool: `unrar x -o+ <archive> <dest>/` for `.rar`; `7z x -y -o<dest> <archive>` for `.7z`, where `7z` is the first of `shutil.which('7z')`, `shutil.which('7zz')` (Ubuntu 24.04's `7zip` package installs `7zz`); and the 7z binary also for `.rar` when `unrar` is absent (its non-zero exit is reported as is, since the rar codec is a separate package). No inflated-size check is possible for these two; the operator's disk is the cap, and the message says so on a non-zero exit. When nothing suitable is on PATH the refusal names the packages: for `.rar`, `apt install unrar` first, or `apt install p7zip-full p7zip-rar`; for `.7z`, `apt install 7zip` (or `p7zip-full`); on Windows, 7-Zip's `7z.exe` on PATH. Rejected: vendoring a pure-Python rar or 7z reader, because both formats need a decompressor the stdlib lacks and the packs that ship as rar are a minority worth one apt install; tar, because no pack in the wild ships that way and every accepted kind should be one a charter actually uses.

**Zip names.** A member without the UTF-8 flag (bit 11 of `flag_bits`) was decoded as cp437 by `zipfile`; Windows-made archives with `Mötley Crüe - Kickstart My Heart` in them arrive as `M├╢tley Cr├╝e`. `fix_member_name(name, flag_bits)` tries `name.encode('cp437').decode('utf-8')` for such members and keeps the repair when it succeeds, the original otherwise (verified on this interpreter). The tool computes each target path itself, so `zipfile`'s own sanitising (which only `extract()` applies) never runs; the rule is: split the repaired name on `/`, drop empty and `.` components, refuse any `..` component and any name starting with `/`, then `resolve()` and require the extraction directory as a parent. A member that fails is skipped and counted, and the run prints `N members outside the archive root skipped`. Directory entries are not written; empty folders in an archive carry nothing the pipeline reads. Bodies are streamed with `zf.open(member)` into the computed path.

**Downloads.** `urllib.request` with a 60 s socket timeout, a `User-Agent: fretwork-ingest`, streamed in 1 MiB chunks through a `tqdm` bar into `caches/ingest/<name>.<suffix>`, no retries. Refused in pre-flight: a host in `NOT_DIRECT` (`drive.google.com`, `docs.google.com`, `mega.nz`, `mega.co.nz`, `discord.com`, `discordapp.com`, `cdn.discordapp.com`), with the message that these are pages or expiring links, not downloads, and the operator should download in a browser and pass the file. Refused on the first response: a `Content-Type` starting `text/html` (a landing page, a Dropbox `?dl=0`, a login wall), a `Content-Length` over `--max-bytes` (default 10 GiB; packs with audio run to tens of gigabytes, and the archive has to fit on disk twice), and a redirect off `https` onto `http` (urllib follows redirects; the final URL is checked). The stream is also cut at `--max-bytes` when there was no `Content-Length`, and the partial file removed. Rejected: retries, because a pack download that fails once fails the same way twice and the operator should see the error; `requests`, because it is not in `requirements.txt` and urllib does this in thirty lines.

**Finding the songs.** While staging, any file whose lower-cased name is in `sanitize_songs.KEEP` is renamed to the lower-cased name (`Song.ini` to `song.ini`, `Notes.MID` to `notes.mid`); two files in one folder that collide after lowering (`Song.ini` beside `song.ini`) are a refusal naming the folder. A song folder is then any directory holding a file named exactly `song.ini`, which is the same walk the parsers do (`rglob("song.ini")`, case-sensitive on Linux), so the tool's `song.ini found` and build's `Song.ini count` are the same number for the same tree; the sanitizer's lower-cased `KEEP` test is looser and harmless after the rename. Zero song folders is a refusal that also says how many `.sng` files were seen, because an Enchor download is exactly the case that hits this. If the extracted root holds exactly one entry and it is a directory, that wrapper is stripped: its contents become the pack. This is the rule the existing library never had (1,253 of 1,758 songs sit under a wrapper). Rejected: flattening every song folder to `songs/<name>/<song>/`, because sub-pack folders (`CSC Quarterly Pack - 1st Quarter 2026` has 5 songs one level deeper) carry meaning a charter chose, and the parsers do not care about depth.

**Staging, sanitising, then placing.** The extraction directory is `caches/ingest/<name>/`. A directory `SOURCE` is copied into it with `shutil.copytree(ignore=...)`, the ignore callback built from `sanitize_songs.classify` (a directory is a song folder when any of its names lower-cases into `KEEP`), so audio is never copied even once: the operator's folder is never modified, which matters because the Windows Clone Hero library is mounted read-only and a pack in someone's Downloads is theirs. Then the sanitizer runs on the staged tree with `apply=True` and `log=caches/ingest/<name>_removed.csv` (for a folder source it mostly reports `0 B`, and still drops the junk names), and only then is the tree moved into the library: `os.replace` (a rename) when `caches/` and the library share a filesystem, and on `OSError` with `errno.EXDEV` a `shutil.move` (copy then delete) with one printed line saying the library is on a different filesystem from `caches/` and the pack was copied; the staging folder is removed only after the copy completes. The rename is the single commit point: everything before it can be re-run, and everything after it is chart-only, so a crash or Ctrl-C never leaves audio, or a half-extracted pack, under `songs/`. `--name` is used verbatim as the folder name and as `folder` in `packs.toml`. Rejected: extracting under a `tempfile` directory, because it can be on a different filesystem (tmpfs on many distributions), in which case a 30 GB pack would be copied rather than renamed; extracting inside `songs/` itself, because a crash would leave a folder full of `song.ini` that the next build scans as a pack; sanitising after the rename (the previous draft), because the window between the rename and the last delete is the same crash for a full pack. `caches/` is already gitignored and already the home of working files.

**The sanitizer callable.** `main()` is split into `sanitize(root, apply, log, show_unknown) -> Report` plus a thin `main()`; both `sys.exit`s (`not a directory`, no song folder) become `ValueError` with the same messages, and `main()` turns either into `sys.exit(str(e))`. The tool imports the module (`tools/` is `sys.path[0]` for a script in `tools/`, and the repo root is inserted beside it). `--dry-run` calls it with `apply=False` on the staged tree, which is the report the sanitizer already prints, and stops before the rename; the staging folder is removed.

**Recording.** The tool builds `packs.Pack(name=args.name, folder=args.name, source=source, added=datetime.date.today(), notes=args.notes)` and calls `packs.append_pack(args.packs, pack)` right after the rename, when the folder is not yet registered. It writes no TOML itself: section 03's `append_pack` serialises, re-loads and raises `PacksError` on a parse failure or a duplicate, and is the only writer of the file. Rejected: writing the entry only after a successful build, because the entry describes a folder that exists from the placing step on, and a failed build followed by a hand-run `build.py` should not also need a hand-written entry; a second serialiser in the tool (the previous draft's `PACK_FIELDS` and temp-copy round-trip), because two writers for one hand-edited file is exactly the drift the tuple comment admitted to.

**Build and analyze as subprocesses.** `[sys.executable, str(REPO / 'build.py'), '--search-path', str(library), '--header', header]` then `[sys.executable, str(REPO / 'analyze.py'), '--header', header]`, cwd inherited, `check=True`, stdout not captured so the tqdm bars show. The tool prints each command verbatim before running it, so the manual route in README sections 2 and 3 stays identical, and it parses nothing from their output: every number in the summary comes from the caches. Rejected: calling `build.build_cache` and `analyze.analyze` in-process (the docs-tooling map's suggestion), because the process pools, pandas and openpyxl then load into the tool's process, the README's commands and the tool's would be two code paths to keep equal, and a subprocess failure is a clean exit code with the traceback already on screen.

**The summary diff.** The previous cache (`timestamp.latest_output('cache', header)`, may not exist on a first ingest) is loaded before build, since a build in the same minute overwrites it (`TS_FORMAT` is minute-resolution). After analyze, the newest cache by mtime must have an mtime at or after the tool's start time, else the run fails with `build wrote no new cache`; a same-minute run reuses the previous path with a newer mtime, which passes. The diff counts songs, charts scored (codes whose instrument letter is not `D`, the codes analyze keeps at `analyze.py:126`), drums cached, Expert charts per instrument, and, for the new pack alone, `song.ini found` against `cached` (the difference is "no usable chart or mid", the count `build.py:151` prints without saying which); the pack's cached count and chart count come from `packs.resolve(cache, registry).songs_by_folder[folder]` and `packs.tally(resolved, codes)` with `codes` the non-drums codes of the cache, so the tool and `python -m functions.packs` agree by construction. Errors come from the newest `caches/<header>_errors_*.csv` whose mtime is at or after the tool's start (never from the cache's stamp, which can differ by a minute from the CSV's); none means zero. The CSV mixes file paths (parse errors, relative when `--search-path` was) and folder paths (`EmptyStream`, absolute), so each row's path is `Path(row['path']).resolve()` against the cwd build ran in before the prefix test `str(path).startswith(str((library / folder).resolve()) + os.sep)`; the rows inside the pack are counted separately.

**Ending.** The tool prints the next commands (`publish.py --header <header>`, `deploy.py --dry-run`, `deploy.py`) and stops. Rejected: `--publish` and `--deploy` flags (the previous draft), because the catalogue line ends at "build and analyze out, with a summary diff", the flags saved one copy-paste each, `deploy.py` takes its header from `.env` or `config.HEADER` rather than a flag (`deploy.py:90`), so a hand-off would have to re-check that against `--header` or risk deploying the wrong library, and `publish.py` reads the repo's `packs.toml` (section 03), so a run with a non-default `--packs` could never be handed to it anyway.

**No `--sng`.** `.sng` is not readable by the parsers, and the tool says so where it matters (the zero-song-folders refusal, and a count in the summary when a mixed pack has some). See Out of scope.

## Data and interfaces

**Command line** (`tools/ingest_pack.py`):

```
python tools/ingest_pack.py SOURCE --name NAME [--source URL] [--header Local]
                            [--library songs] [--packs packs.toml] [--notes TEXT]
                            [--replace] [--dry-run] [--max-bytes N]
```

| Flag | Meaning | Default |
|---|---|---|
| `SOURCE` | `.zip` / `.rar` / `.7z` path, a directory, or an `http(s)` URL to one of those | required |
| `--name` | folder under the library; also `name` and `folder` in `packs.toml` | required |
| `--source` | the URL recorded in `packs.toml`; `''` or `http(s)://` only | the URL when `SOURCE` is one, else `''` |
| `--header` | the run identifier handed to build and analyze | `Local` |
| `--library` | the library root, handed to build as `--search-path` (resolved to absolute) | `songs` |
| `--packs` | the registry file, passed to `packs.load` and `packs.append_pack`; anything but the default is for tests, since `publish.py` reads `packs.PACKS_FILE` | `packs.PACKS_FILE` |
| `--notes` | free text for the entry | `''` |
| `--replace` | replace an existing `<library>/<name>/`; appends an entry only when the folder is not yet registered | off |
| `--dry-run` | fetch, extract, find, report the sanitizer's dry run, stop; nothing under the library or in `packs.toml` changes | off |
| `--max-bytes` | download cap, and the cap on a zip's summed `file_size` | `10737418240` (10 GiB) |

Exit status 0 on success, 1 on any refusal or subprocess failure, with the refusal on one line starting `refused:`. Path arguments resolve against the cwd; `caches/` and `metrics/` land there too.

**Working files**, all under `config.OUTPUT_DIRS['cache']` (`caches/`, gitignored) relative to the cwd: `caches/ingest/<name>.<zip|rar|7z>` for a download (kept on success so a re-run with `--replace` can reuse it; the tool says it is there), `caches/ingest/<name>/` for extraction (removed after the rename; a leftover from a crashed run is removed at the start of the next run, with a line saying so), `caches/ingest/<name>_removed.csv` the sanitizer's log, which names staging paths.

**`packs.toml`** (repo root, committed; the file, its reader and its writer belong to section 03). One `[[pack]]` per ingest, appended, newest last, exactly what `append_pack` writes:

```toml
[[pack]]
name = "CSC Quarterly Pack - 2nd Quarter 2026"
folder = "CSC Quarterly Pack - 2nd Quarter 2026"
source = "https://example.org/csc-q2-2026"
added = 2026-09-11
notes = ""
```

`name` and `folder` are the same string at ingest (`--name`); `folder` is the exact directory name under the library and is the join to the cache. `added` is `datetime.date.today()`, a bare TOML date. Uses `packs.Pack`, `packs.load`, `packs.append_pack`, `packs.resolve` and `packs.tally` as 03 defines them, and `packs.PacksError` for the pre-flight message.

**Section 03 must add:** `append_pack` writes to `<path>.tmp`, re-loads that, and `os.replace()`s it into place only when the reload passes, so a bad append never lands in the committed file; a failed append raises `PacksError` with the file untouched. Nothing else.

**`tools/sanitize_songs.py` callable:**

```python
Report = namedtuple('Report', 'song_folders total_bytes removed_bytes removed_files failed unknown')
# unknown: list of (Path, size) left alone inside song folders

def sanitize(root: Path, apply=False, log: Path | None = None, show_unknown=False) -> Report
```

`sanitize()` prints the report exactly as `main()` does today and raises `ValueError` (not `sys.exit`) for a root that is not a directory and for a root with no song folder, with today's two messages; `main()` keeps the argparse surface and turns either into `sys.exit(str(e))`. Every module-level name (`KEEP`, `REMOVE`, `JUNK_NAMES`, `classify`, `scan`, `human`) is unchanged.

**`ingest_pack.fix_member_name(name: str, flag_bits: int) -> str`**: the cp437 repair, and **`ingest_pack.preflight(args) -> Plan`**: every refusal of the pre-flight paragraph, raising `Refusal(message)` which `main()` prints as `refused: <message>` and exits 1 on; both exported for the tests. `Plan` carries the decided state: the source kind, the registry, whether the entry will be appended or kept, and whether the folder will be removed.

**Summary output**, the format the tool prints; the before/after numbers are the two newest Local caches on this box, which differ only by drums (the pack lines are illustrative):

```
Summary  Local  09072026-2031 -> 09112026-1502
  songs                    1,758 -> 1,758      +0
  charts scored           11,904 -> 11,904     +0
```

## Risks and gotchas

- **Minute-resolution stamps.** Two builds in the same minute produce the same cache filename (`functions/timestamp.py:13`); the second overwrites the first. The tool loads the previous cache before building and checks the newest cache's mtime against its own start afterwards, but an operator who runs `build.py` by hand in the same minute as the tool gets one cache, not two. The errors CSV is found by mtime for the same reason (`build.py:145` and `:160` stamp separately).
- **Codes move on re-ingest.** A pack re-ingested under a different `--name`, or one whose wrapper is now stripped, changes every code in it (path hash, `functions/cache.py:61-63`), which changes graph filenames and any shared `?code=` link. With `--replace` under the same name the codes usually survive: they hash the resolved path, and only a hash collision with a new song (linear probing, `functions/cache.py:78-81`) can move one. Section 05's `SongKey` is the stable identity; until section 10 the summary cannot say "these 6 are copies".
- **`--replace` is a delete.** It removes `<library>/<name>/` before placing, after the staged tree is already sanitised, so the library is never without the pack for longer than a rename. The tool prints the folder and the song count it is about to remove; there is no prompt, because the script runs unattended in CI.
- **`unrar`/`7z` output paths.** Both tools honour the destination flag, but `7z` treats `-o` without a space as the only form; the argument is built as one string `f'-o{dest}'`. Neither is on the dev box today, so the rar and 7z branches are verified on the first real rar pack, and the test suite covers only the refusal message.
- **Downloads without `Content-Length`** (chunked transfer) are cut at `--max-bytes` with a partial file removed; a Dropbox or GitHub release direct link sends the length, a Cloudflare-fronted host may not.
- **`deploy.py` reads its header from `.env`** (`FRETWORK_HEADER`, falling back to `config.HEADER`, `deploy.py:90`), not from a flag. The `Next:` block prints `deploy.py` under the header the tool used; the operator's `.env` must name the same one, and README step 4 says so. The tool itself never reads `.env`.
- **Backup CSV drift (section 00).** Before the fix, the first new song appends a 7-field row under a 6-field header (`build-parsers-cache` map, `functions/ini_updater.py:19,157-162`); this tool is the first thing that adds a song. Ingesting before 00 lands corrupts nothing the site reads, but `Restore` would then silently skip `diff_drums` for those songs.
- **The sanitizer's unknowns.** `original.mid`, `notesold.mid`, `song (1).ini` and `idk.chart` are left in place by design and ignored by the parsers (`rglob` on the exact names). They travel into the library and are harmless; the summary's sanitizer line does not list them, the sanitizer's own report does.
- **A pack that is a folder of packs** (a "CSC Monthly 2024" archive holding twelve month folders) ingests as one `packs.toml` entry, because `--name` is one folder. If the changelog should list months separately, ingest each month as its own archive; the tool does not split.
- **An absent `--packs` file** is created empty only when it is not the default; the repo's `packs.toml` missing is a refusal, since section 03 committed it and its absence means the wrong working directory or branch.
- **A non-default `--packs` and publish.** `publish.py` reads `packs.PACKS_FILE` (section 03) and exits on a cache folder the repo file does not name, so a pack recorded in another registry is not publishable until its block is in the committed file. The tool prints that warning above the `Next:` block whenever `--packs` is not the default.
- **Non-ASCII on Windows consoles.** Song names print through `tqdm` and `print`; on a cp1252 console a `Mötley` line raises `UnicodeEncodeError`. The tool sets `sys.stdout.reconfigure(errors='replace')` at start, as the other entry points do not, because this one prints paths from other people's archives.

## Out of scope and follow-ups

- **Optional follow-up: `.sng` unpacking.** Enchor serves single-file songs (`files.enchor.us/<md5>.sng`), which the parsers cannot read: `ini_loop` and the note loops `rglob` for `song.ini`, `notes.chart` and `notes.mid` on disk. The `.sng` container is documented by the sng-parser project (a header with a version, a metadata block of key/value pairs that is the `song.ini` content, then a file table and XOR-masked file bodies); `sng-parser` on PyPI reads it (1.3.0 current), and `encore-python` 1.1.0 pins `sng-parser==1.1.0` plus `requests` and `jsonobject`. Decision when this is picked up: write a minimal reader in `tools/sng.py` (header, metadata to `song.ini` text, file table, unmask, extract only `notes.chart`/`notes.mid`), not vendor sng-parser, because the pipeline needs about eighty lines of the format and none of the client's dependencies, and `requirements.txt` stays as it is. The fact that unblocks it: one real `.sng` from Enchor to check the mask and the metadata encoding against, since neither the container's exact byte layout nor how `sng-parser` writes `song.ini` keys back is verified here. The tool would then accept `.sng` files inside an archive (each becomes `songs/<name>/<title>/song.ini + notes.*` before sanitising) and the "no song folders" refusal would stop mentioning `.sng`.
- **Optional follow-up: copies in the summary.** Once section 05's `song_key` is in the cache and section 10 defines copies, the `this pack` block gains `copies of songs already listed: N`; the join is `song_key`, computed in build, so the tool only counts.
- Incremental build: not this section. The parsers are per-file and the cache is one pickle; a cache that merges per-pack results is a build change that would also have to keep code assignment's linear probing stable (`functions/cache.py:78-81`). The measured parser cost (about 37 s single-process for the whole library) says the full rebuild is cheap enough not to need it.
- `--publish` and `--deploy` hand-off flags: rejected under Design; the `Next:` block is the hand-off.
- Removing a pack: `rm -rf songs/<name>`, delete its `[[pack]]` block, build and analyze. The tool does not do it; a removal is rare and the two commands are in README sections 2 and 3.
- Ingesting straight from a GitHub issue (reading the form's link field through `gh issue view`): the link is usually a page, not an archive, and the operator has to visit it anyway.
