**Status:** Ready

## Goal

Close five small correctness holes found while mapping the repo, each as its own commit with its own proof, so that every later section starts from a tree where: publish works against the newest cache and refuses a cache and spreadsheet from different builds; `serve.py` answers exactly the four pages `publish.py` writes; a drums code renders "no graph" instead of a traceback; the backup CSV cannot drift out of step with its own header; and `page.fill` cannot be tripped by a song title. Two pieces of housekeeping ride along: paying for the fingerprint change in `69b5a8f` with one full re-render, and deleting the merged `hosting` branch.

## Why

- Every later section (02 through 13) publishes, and most of them serve locally first. Section 05 states its dependency on this section outright: it reuses the serve routes for `about.html`, `404.html` and `robots.txt`, the pairing refusal, and the drums lookup guard.
- Three of these are latent crashes that a visitor or a maintainer can trigger with one request or one command: `render.py <code>XD`, `curl localhost:8000/graph/<code>XD.png`, the footer's About link under serve.
- One of them silently corrupts a file the user relies on to undo a write-back to their library (`caches/<header>_BackupData.csv`), and it is upstream's file, so the fix is worth carrying upstream.
- The rest are the difference between "the tool warned me" and "the tool stopped me": a mismatched publish would put a table computed from one cache beside graphs rendered from another.

## Design

Seven items, five of them code. Each is the smallest change that makes the failure impossible rather than merely handled, and each stays inside the module that already owns the behaviour.

**(a)** Nothing more to change in code. The next publish re-renders every chart because every fingerprint changed; that is correct behaviour, and it runs once. Rejected: seeding the manifest with recomputed hashes to skip the render, because the cache also moved from 2031 to 2324 and the PNGs may genuinely differ; the render is the only thing that can tell. Rejected: reordering the tuple to keep old hashes valid, impossible since the removed element carried data.

**(b)** A one-time header migration inside `ini_updater`, run from the two write paths (`backup_data` and `restore_from_backup`) and once more from `build.build_cache` before the parse loop, never from the read-only `load_backup_diffs`, so render, serve and publish never rewrite a file under `caches/`. The `build.py` call is there because `backup_data` runs at `build.py:111`, after several minutes of parsing and before the cache is saved; a refusal has to come in the build's first second, not its last. Three cases, decided by comparing the file's header with `BACKUP_COLUMNS`: the header is a proper prefix of `BACKUP_COLUMNS` (an instrument joined `DIFF_TAGS`), so rewrite the file with the new header, `''` in each new column for existing rows (the same value `backup_data` writes for an instrument the song does not chart, `:152`), and the values of any row that already drifted recovered by position (a `DictReader` puts extra fields under its `restkey` in the order they were written, which was `BACKUP_COLUMNS` order); `BACKUP_COLUMNS` is a prefix of the header (a file written by a newer instruments table, say `upstream/drum-staging` or a future vocals tag), so leave it alone, since `DictWriter` writes shorter rows under it without complaint and `DictReader` fills the missing names with `None`, which `restore_from_backup` (`:183`, `if row.get(diff_tag)`) and `load_backup_diffs` (`:133`, `or '-1'`) both treat as blank; anything else is refused with `ValueError`, since guessing about a file whose purpose is to undo writes to the user's library is worse than stopping. A missing file is left alone too. The append-only rule stands: rows are never re-derived from the library, and dedup by `song_path` is untouched. Since both files are upstream's and identical on both sides, the change is made on a branch cut off `upstream/main`, merged into the fork's `main` with `--no-ff`, and offered upstream as a pull request. Rejected: rewriting the header only when the first new row is appended, because a Restore run before any build would still miss the column; rewriting the whole file on every build, because the file is append-only by design and a 200 KB rewrite per build is noise in `git status`-style diffs of `caches/`; backfilling `diff_drums` from the current `song.ini` files, because the code cannot know that no write-back has happened (today it has not, see Out of scope); refusing a longer header, because it needs no change and refusing it would fail every build for a user who has been running a newer tree.

**(c)** One predicate, `difficulty.scorable(notes)`, next to the function that defines what a scored chart is, and three callers: `entry_difficulty` returns `None` (its documented "no usable notes" outcome), `GraphRenderer.lookup` returns `None` (its documented "unknown code" outcome, which the handler turns into `404 no graph for that code` and publish counts as `no_graph`), and `render.py` prints `[skip] <code>: <instrument> is not scored yet` beside its existing `no curve data` skip. `bundle.GraphRun.one` is covered by `lookup`. Section 11 removes the two guards the day drums are scored (see Risks). Rejected: filtering drums out in `cache.entries_by_code`, because that is upstream's file, because a resolved code is the truth (the chart exists, it is just not scored), and because section 11 will want those entries back; guarding inside `density.window_arrays`, because it is upstream's and because returning `None` there would make analyze silently skip drums forever without the deliberate line at `analyze.py:126`; catching the `KeyError` in the handler, because the exception is a shape error and the fix belongs where the shape is known.

**(d)** Serve serves exactly what publish writes. The four-page dict that `publish.py:58-60` builds moves into `page.site_pages(body)` and both entry points call it; the server carries `pages` instead of `body`; the handler serves any path in that dict with the content type its extension implies, and answers everything unknown with the `404.html` bytes and status 404. What section 04 takes from this is a Python assertion that `MetricsServer` on port 0 answers `/about.html`, `/robots.txt` and an unknown path with 200/200/404 and bytes equal to publish's files; its page suites run against the bundle under `http.server` and do not use serve. This is the seed of section 05's `Built.files` dict and is replaced by it. Rejected: adding `*.html` to `STATIC_GLOBS`, because the templates are unfilled and must not be served raw; special-casing `about.html` alone, because `robots.txt` and the 404 page have the same split and section 05 needs the general route.

**(e)** `check_pair` raises `SystemExit` on a mismatch unless `allow_mismatch=True`, exposed as `--allow-mismatch` on `publish.py` and deliberately *not* on `deploy.py`: a mismatched bundle that must go out anyway is published by hand with the flag and then sent with `deploy.py --no-publish`, so the decision is taken twice. Names that do not follow `{header}_{kind}_{timestamp}` (an explicit `--xlsx` or `--cache` path from elsewhere) cannot be compared; that prints a note and proceeds, as today. The check stays where it is in `publish()`, after `page.build` and `renderer.cache()`: both are reads, nothing is written before `bundle.write_page` at `:61`, and moving the check earlier would mean resolving the paths twice. Rejected: comparing `cache['generated_at']` with the xlsx, because analyze already copies the cache's filename timestamp onto the xlsx (`analyze.py:174-175`) and that is the contract README section 7 documents; making it a warning with a countdown, because nobody reads a countdown.

**(f)** `fill` checks the template against the values before substituting: every placeholder name in the template must have a value (catches a typo or a missing value), and every value must be named by the template (catches a placeholder the regex cannot see, which is exactly the `288d6a4` bug, where `__LICENSE_URL__` did not match `[A-Z]+` and so was neither substituted nor detected). Because substitution is one pass, a value's text is inserted verbatim and never re-scanned, so with both checks passing no placeholder can survive, and the output need not be scanned at all. Rejected: scanning the output outside the boot island, because it means parsing the page the code just generated; escaping underscores in the data, because it changes what the page shows.

**(g)** Delete `hosting` locally and on `origin`; keep `screenshots`, because four images in upstream PR #6 resolve through that branch name and that thread is the launch record (section 01 posts there once); keep `origin/cleanup` as CLAUDE.md says. Rejected: tagging `6072142` and deleting `screenshots`, because the PR body names the branch, not a tag, and editing a closed PR's body on another repository to chase a URL is work for no gain. Needs the user's go-ahead before anything is deleted.

## Risks and gotchas

- Step 6 is the only long step and the only one that touches `site/Local/`. Do not run it with `--force`: the manifest rewrite is what proves (a), and `--force` would prove nothing.
- `write_if_changed` keeps mtimes only when the bytes are identical. matplotlib renders were measured byte-identical across two runs of the same inputs, so most PNGs will not upload; but the cache moved from 2031 to 2324 across an upstream parser change, so some will. The dry run in step 6 is the measurement; do not guess the number.
- `check_pair` compares filename timestamps while `latest_output` chooses by mtime. A copied or touched old cache is "newest" and will fail the check against a newer spreadsheet; the message names both timestamps, which is enough to see what happened.
- `SystemExit` from `check_pair` propagates through `deploy.py`'s call to `publish()` at `deploy.py:180`, before any `aws` command runs; `check_site` has already passed by then, so nothing is half-done.
- The 404 page's links are root-absolute (`/static/favicon.svg`, `/`), which is right for CloudFront and for serve at the root, and wrong under `python -m http.server` from a sub-directory; that was already true of the published file.
- `backup_data` runs at `build.py:111`, after parsing and before `cache_mod.save` (`:146`), so without the `build_cache` call an unrecognised header would abort a multi-minute build with no cache written. The one line before `ini_loop` is what moves that refusal to the first second; it is a change to upstream's `build.py` and travels in the same commit and PR as the `ini_updater` change. Both call sites reach the function with no file on a fresh header (`backup_data` before the first build; `restore_from_backup` only after its own `FileNotFoundError` check at `:171-172`), and the function returns `False` there.
- `migrate_backup_header` is called from `restore_from_backup`, which analyze's `--diff-mode Restore` runs before touching any `song.ini`. It rewrites `caches/<header>_BackupData.csv` first; if the header is unrecognised it raises and Restore does nothing, which is the safe order.
- A user of upstream who built after `e9ec963` (2026-09-08, when `diff_drums` joined `DIFF_TAGS`) on a library that already had a backup CSV has drifted rows today; the by-position recovery is for them. It relies on `DictWriter` having written the extra fields in `BACKUP_COLUMNS` order, which is the only way `backup_data` writes.
- `entry_difficulty` returning `None` for drums matches its existing contract. `analyze.py` does not call it (it goes through `density` and `formula` itself, and skips drums at `:126`), and `render.py:64` and `web/graph.py:56` only reach it after the new skip and the lookup guard, so no caller sees the new `None` today. Section 11 removes the guard from `GraphRenderer.lookup` and `render.py` once every cached stream is flat, and flips section 04's `...XD is 404` assertion to 200; whether `difficulty.scorable` itself survives as a shape assertion is section 11's call.
- `render.py` is a shared file both sides edit (it already differs from `upstream/main` by 16 lines); keep the skip to two lines directly beside the existing `no curve data` skip at `render.py:59-61` so an upstream change to that loop conflicts trivially, and re-check it after every `git merge upstream/main`. CLAUDE.md expects merge conflicts only in `README.md`, `.gitignore` and `CLAUDE.md`, so this is the one exception to watch.
- `fill`'s `unused` check makes every value mandatory. `render_about` passes `META` and the 404 template has no `META`; keep each renderer's `values` dict exactly matched to its template, which is the point.
- The `-d` in step 7 is the safety: if `git branch -d hosting` refuses, something was not merged and the step stops there.
