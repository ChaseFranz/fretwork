## Goal

Every chart the site rates gets, where one exists, a link to where the chart is published (Chorus Encore, `https://enchor.us/chart/<md5>`) and a link to its Clone Hero leaderboard (`https://leaderboards.clonehero.net/scores/<songHash>`). Both are resolved offline by two tools in `tools/`, written to one registry file per header, published as one small immutable JSON file, and shown as two anchors beside the report link in the graph modal (and in whatever heading sections 06 and 07 give that modal and the song view). The visitor's browser never contacts either service until they click.

## Why

- The about page says plainly that nothing can be downloaded here (`functions/labels.py:249-253`). The next question a visitor asks after "how hard is it" is "where do I get it", and today the answer is a search on another site with the title copied by hand.
- The leaderboard is the other half of the difficulty story: a chart's D beside how many people have full-combo'd it. The userscript at `../fretladder-leaderboards.user.js` (the Tampermonkey prototype kept beside the repo, untracked) already does this join in the browser, for one person, at 50 requests a minute, and breaks the moment section 05 moves the rows out of the page (below). Doing the join once, offline, gives every visitor the link and removes the third-party request from the page.
- Neither service's API should be called from the page: api.enchor.us is CORS-open (`access-control-allow-origin: *` in the captured headers), api.clonehero.net is not known to be, and both limit to 50 requests a minute (captured `x-ratelimit-limit: 50`; userscript line 29). A page that makes a request per opened graph would exhaust that on a busy evening and would tell two more sites who is reading fretladder.

## Design

**1. Everything is resolved offline; the page only reads a file.** Two tools under `tools/` talk to the two APIs at 48 requests a minute and write their answers into one registry, `caches/<header>_links.json`, which persists across builds like `caches/<header>_BackupData.csv` does (no timestamp, append-only in spirit, keyed by song). Page-build turns the registry into `data/links.<hash8>.json` under section 05's immutable class. The page fetches that file after the sheets and reads it when a graph opens. Rejected: a view-time fetch for charts missing from the file, even though api.enchor.us is CORS-open, because the site would then make third-party requests the about page does not disclose and would spend a shared 50-a-minute budget on behalf of every visitor. Rejected: the userscript's approach of resolving in the browser, for the same reasons plus the 05 breakage.

**2. Per-song file, not per-row columns.** The brief asked for a hidden `Enchor` column; the measurement above says two columns cost about half a megabyte gzipped across the sheets and a per-song file costs under 100 KB once. Both keys are per song anyway (Enchor's `md5` is a folder, the leaderboard's `songHash` is a song). So the page gets `data/links.<hash8>.json` keyed by `SongKey`, and the row supplies the `SongKey` the modal looks up. Rejected: keying the published file by the 8-digit code, which changes on every re-download (`cache.py:61-63`) and would orphan the file at the next pack move.

**3. The Enchor key is the raw file MD5, stored at build.** `chart_md5 = hashlib.md5(pathlib.Path(source).read_bytes()).hexdigest()`, computed at the top of `chart_parser.chart_notes` and `mid_parser.mid_notes` as a second read of the file inside the worker: neither function has the bytes in hand (`parse_chart` opens the file in text mode with `encoding='utf-8-sig'`, `parsers/chart_parser.py:79`, and `mid_notes` hands the path to `mido.MidiFile(str(mid_source), clip=True)`, `parsers/mid_parser.py:252`), and the hash must be over the raw bytes, BOM included, as Enchor would see them, not over decoded text. It is added to the return dicts at `parsers/chart_parser.py:258-263` and `parsers/mid_parser.py:295-300`, the parsers' own reads stay unchanged, and `build.py` copies it onto the song dict (`build.py:104-109`) beside `source_format`, never into `meta` (fingerprint, above). Chart wins over mid at `build.py:39`, so when a folder ever holds both, the hash is of the file fretwork parsed, which is also the file Enchor would parse. It is not an xlsx column and not a page column: the Enchor tool reads it from the cache, the page never needs it. Rejected: hashing in `build.py` after the pool, which would re-read 180 MB serially; hashing in the workers costs 0.31 ms against a 6 to 25 ms parse.

**4. The probe decides the Enchor half.** `tools/enchor_probe.py` is a one-off that takes song folders on the command line, hashes each notes file, asks `/search/advanced` with `chartHash` set to that one hash, then once more with all hashes comma-joined, and prints a table: folder, format, `chart_md5`, `found`, and for each hit `md5`, `chartId`, `name`, `charter`, Enchor's `noteCounts` for `guitar`/`expert`, and the cache's Expert Lead `len(time_ms)` for that folder. Five folders: three from `CSC Quarterly Pack - 4th Quarter 2025` (two `.chart`, one of its four `.mid`), one from `S Hero`, and one official `.mid` from `Guitar Hero III (Individual Songs)` as a control. Yes means the four customs each come back with one hit carrying a 32-hex `md5` and the batch request returns the same four; the control's answer is printed and recorded but is not part of the yes/no, since nobody has checked whether Enchor lists official rips. No means the filter is over other bytes; then the Enchor half falls back to the same metadata join the leaderboards use (`name` and `artist` filters with `exact: true`, then `charter`, then `notesData.noteCounts` for `guitar`/`expert` against the row's Expert Lead `NoteCount`), one request per song, recorded with `"via": "meta"` instead of `"via": "md5"`; everything downstream of the registry is the same. Two side questions ride the same run. First, the probe sends one more request with `chartHash` set to the `chartHash` string of one hit (the blake3 value) and records whether that filters to the same chart; if it does, the fallback question becomes blake3 (a non-stdlib dependency, rejected under CLAUDE.md's rule) against metadata, and the answer is written beside the MD5 result. Second, the two note counts per hit decide the batch match-back rule in Design 5. The probe also records the first response's rate-limit headers and whether a 100-hash batch is accepted (`400`/`413` mean halve it), which fixes `--batch` for step 3.

**5. Batches for Enchor, singles for the leaderboards.** `tools/enchor_lookup.py` walks the cache's songs, skips any `SongKey` the registry already answers (hit or miss) unless `--recheck`, and posts `chartHash` lists of `--batch` hashes (default 100, the probe may lower it) with `per_page: 250`, paging when `found` exceeds the page. The response carries no chart-file MD5, so a batch answer cannot say which request hash produced which hit; hits are therefore matched back by the response's `notesData.noteCounts` (Expert Lead) plus normalised `name`/`artist` against the cache's meta and Expert note count, and any hit that matches no request hash is logged and dropped. That rule is conditional on the probe: if Enchor's count agrees with the cache's `len(time_ms)` on all four customs, it is used as written; if the two disagree by a constant rule (fret events rather than timestamps, say), `links_common.enchor_count(entry)` reproduces Enchor's count from the stream and the match-back uses that; if they disagree with no rule, the match-back is title, artist and charter only, and a batch holding two charts with the same normalised title and artist sends those singly. If the probe shows the response does carry a chart-file MD5 field, the tool matches on that instead and the count check becomes an assertion. When one hash yields several hits (the same chart file uploaded with different audio has one `chart_md5` and several Enchor `md5`s), the hit with the largest `chartId` (the newest upload) is recorded with `hits: n`, so two runs give the same link. Songs sharing a `SongKey` are asked in sorted `song_path` order and the first answer is kept. 1,758 songs at 100 a request is 18 requests, under a minute. `tools/leaderboards_lookup.py` ports `norm`, `songKey` and `pick` from the userscript to Python, walks the newest spreadsheet grouped by `SongKey`, takes the row whose `Type` is `instruments.TYPE_LABELS['guitar']` at Expert (else the first Expert row of any type, its instrument recovered through the inverse of `TYPE_LABELS`, never by the literal `Lead`) for title, artist, charter and `NoteCount`, does one quick search per song, records `candidates: n` (the length of the same-title-and-artist pool), and then: for a pool of one whose charter matches, no more requests; for a pool of one whose charter does not match, the one `/scores` call the userscript makes at 343-345 (`instrument` from `LEADERBOARD_INSTRUMENT` for the row used, `difficulty=expert`), and `sure` is true when the top score's `noteCount` equals the row's `NoteCount`, with `charter_matched: false` and `note_count` recorded; for a larger pool, one `/scores` call per candidate and `pick()` as at 292-320. At 48 a minute that is about 37 minutes for 1,758 songs plus the tail of extra calls; the file is saved every 25 songs so an interruption loses under a minute. Rejected: resolving per row (11,904 requests, four hours, for the same 1,758 answers). Rejected: porting `resolveSongHash` without the lone-candidate confirmation, which would record every charter-drift song unsure and never link it.

**6. Only sure leaderboard matches are published.** The registry keeps every answer with the userscript's `sure` and `twins` flags; page-build emits a `lb` key only when `sure` is true or `twins > 1` (identical notes on several boards, the most-played one first, as the userscript reasons at 313-318). Unsure matches, and nulls whose `candidates` equalled the largest pool seen in the run (a full-looking first page, where the right board may sit on a page the quick search did not return), are listed by `--unsure` for a person to look at and re-query with the charter added to `q`. Rejected: a "best guess" badge on the site; a link from a rating to the wrong song's scores is worse than no link.

**7. Two anchors beside the report link, rendered from state, nothing else moves.** `linkAnchors(songKey)` in `overlay.js` returns the markup for `On Chorus Encore` when `state.links[songKey].enchor` exists and `Leaderboard` when `.lb` exists, both `target="_blank" rel="noopener"`, class `ext`, 11 px like `.rpt`, or an empty string when `state.links` is not loaded yet or the song is absent. Where they go is fixed by section 06's heading table and section 07's wrapper, whichever order those land in: inside `.mhead` line 1, in one `<span class="ms-auto lnk">` (07's name; whichever of 07 and this section lands first creates it, and it takes over `ms-auto` from `.rpt`), holding in DOM order this section's two `.ext` anchors, 07's `.sng` link when present, then `.rpt`, so the links sit together at the right edge and wrap to a second line as one unit on a phone; in 07's `#song` panel, appended to the `p.meta` line after Official|Custom. This section adds no wrapper of its own and moves nothing when 06 lands. The heading is a function of current state, never a cached string: `openGraph()` keeps `const head = () => heading(code)` and calls it in both the loading message and `img.onload`; `heading()` reads `state.links`, so a modal opened after the file has arrived renders the anchors at once; `loadLinks().then(update, () => {})` with `update` replacing only `.mhead` (`card.querySelector('.mhead').outerHTML = head()`, guarded by `state.graph === code`) covers a modal opened before, whichever of the file and the PNG lands second. A rejected links load is swallowed in `openGraph`; the heading is already complete without it. The URL templates live in `labels.UI` and the two hosts are named once at the top of `labels.py` beside `ENGINE_REPO`. The about page's "What is stored here" paragraph gains one sentence saying that where a chart is published on Chorus Encore, or has a Clone Hero leaderboard, the graph links there, and that nothing is hosted here. Rejected: a column with a link icon in the table, because the table is 11,904 rows and a link per row is what the file-size measurement ruled out; the modal and the song view are where one chart is in focus. Rejected: the label `Get this chart`, because the about page says "It is not a place to get songs" and a verb that invites downloading would make that sentence argue with the heading; the label names the destination instead.

**8. The userscript is not updated by this section.** It stays as it is, breaks at section 05, and is listed as a follow-up with its exact dependencies. Once this section ships, its fretladder side is redundant (the site carries the leaderboard link); its leaderboard side (D and tier shown on a board page) remains useful and would read `data/<slug>.<hash8>.json` through the boot manifest instead of the island.

## Data and interfaces

**Cache song dict** (`functions/cache.py` docstring, `:6-38`) gains `'chart_md5': str`, 32 lowercase hex, the MD5 of the raw bytes of the notes file that produced `source_format`. Parser stream dicts (`chart_parser.chart_notes`, `mid_parser.mid_notes` return values) gain the same key. Never in `meta`. Never an xlsx or render column.

**Instrument table** `functions/instruments.py` gains `LEADERBOARD_INSTRUMENT = {'guitar': 'guitar', 'coop': 'guitarcoop', 'rhythm': 'rhythm', 'bass': 'bass', 'keys': 'keys'}`, the leaderboards API's vocabulary (userscript 44), keyed by the five keys of `SONG_KEY_INSTRUMENTS` (section 05) and asserted at import to have at least those keys (a superset, so section 11 can add `drums` when its API literal is known without touching the assertion). It lives here because CLAUDE.md keeps every instrument table in this module (`MID_TRACK_NAMES` and `CHART_SECTIONS` are the precedent for another system's vocabulary); `tools/links_common.py` imports it.

**Registry** `caches/<header>_links.json` (gitignored with `caches/`; `OUTPUT_DIRS['cache']`, `config.py:128-133`), written atomically (temp file then `os.replace`):

```json
{"v": 1,
 "enchor": {
   "3f2a9c1d0b7e": {"chart_md5": "b569c717730c7118005134e9827a7328", "md5": "9c1e...", "chartId": 386212,
                    "hits": 1, "via": "md5", "checked": "2026-09-12"},
   "8b0d4e2f6a91": {"chart_md5": "0d3c...", "md5": null, "checked": "2026-09-12"}
 },
 "leaderboard": {
   "3f2a9c1d0b7e": {"songHash": "TM7lJvm8-cA6-nM9qUsqLzQmHa_VtrDyqtzF85IkOoU", "sure": true, "twins": 1,
                    "candidates": 2, "charter_matched": false, "note_count": 579, "checked": "2026-09-12"},
   "8b0d4e2f6a91": {"songHash": null, "candidates": 0, "checked": "2026-09-12"}
 }}
```

Keys are `SongKey` (section 05, 12 hex). A `null` value means "asked, not found" and is skipped on the next run; `--recheck` re-asks nulls, `--recheck-all` re-asks everything. `via` is `"md5"` or `"meta"`; `hits` is how many Enchor hits the request hash produced (the largest `chartId` is the one recorded). Two songs sharing a `SongKey` with different `chart_md5` are asked in sorted `song_path` order and the first answer is kept, its `chart_md5` recorded. Songs whose `song_key` is `None` (no five-fret stream) are skipped. `charter_matched` is whether the charter text agreed; `note_count` is the board's Expert note count when a `/scores` call was made, else absent.

**Published file** `data/links.<hash8>.json`, built by `web/links.py` from the registry, section 05's `hash8` (first 8 hex of SHA-1 over the bytes written) and slug rules (the slug `links` is reserved; publish raises if a sheet slugs to it):

```json
{"v":1,"songs":{"3f2a9c1d0b7e":{"enchor":"9c1e...","lb":"TM7lJvm8-cA6-nM9qUsqLzQmHa_VtrDyqtzF85IkOoU"},
                "a1b2c3d4e5f6":{"lb":"..."}}}
```

Only songs with at least one link appear; `enchor` is the Enchor `md5`, `lb` the leaderboard `songHash`, each present only when known and, for `lb`, sure or `twins > 1`. ## Risks and gotchas

- The probe can say no. Then Enchor is joined on metadata like the leaderboards, one request per song, 37 minutes, and `via: "meta"` in the registry; the code in step 3 is written with the matcher from `links_common` either way, so the branch is the request builder, not the tool.
- A batch answer carries no request hash back. Until the probe shows a chart-file MD5 field in the response, batch hits are matched by title, artist and (if the probe shows the counts agree or follow a rule) Expert Lead note count against the cache; a batch of 100 with two charts of the same song and count is ambiguous, which the tool resolves by sending those two singly. Do not skip this: a wrong `enchor` link sends someone to a different chart.
- The Enchor evidence is not on disk. The probe's `caches/enchor_probe_<date>.json` becomes the record; do not write step 3 from the line numbers in Current state alone.
- `meta` must not gain `chart_md5`: `bundle.fingerprint` hashes `meta` (`web/bundle.py:76`) and the next publish would re-render 11,904 PNGs. Step 2's check (`0 rendered`) exists for this.
- `chart_md5` is never an xlsx or render column, so the committed examples under `metrics/` and `renders/` are untouched; the only spreadsheet change this section relies on is 05's `SongKey`. No column is added to the page, so `PREFS_VERSION` is not bumped and no localStorage key changes.
- The registry is keyed by `SongKey`, which section 05 warns changes with any tick-to-ms change in `parsers/timing.py`. After such a change the registry's keys are orphaned; `enchor_lookup` notices (every song unknown) and re-asks, 18 requests; `leaderboards_lookup` re-asks 1,758 songs, 37 minutes. The registry also records `chart_md5`, so a `--rekey` that maps old keys to new ones through the cache's `chart_md5` is cheap to add when it is first needed; not written now.
- The registry is about 40 minutes of rate-limited lookups plus any hand corrections, and it is not committed (it describes the real library, which CLAUDE.md keeps out of the repo) and sits in a folder people clean out. Keep a copy outside `caches/` before cleaning that folder; `--links FILE` exists so a copy can be pointed at directly.
- api.clonehero.net's limit is known only from observation (429 after about 50 a minute). The pacer's 48 a minute is a guess at the edge; the first 50-song run measures it. If 429s appear at a lower rate, lower `--per-minute` rather than retrying harder.
- The quick search may not list every board for a common title, and the tool then records a confident null. `candidates` and the full-pool listing under `--unsure` are the guard; a person re-queries with the charter in `q`.
- The leaderboard URL shows whichever instrument the visitor last chose there (`localStorage['instrument']`, userscript 225-226), not the row's. A Bass row's `Leaderboard` link may open on Lead scores; the board page has a query-parameter helper (`getScoreLeaderboardQueryParams` in the Angular bundle) whose parameters were not captured, see follow-ups.
- `enchor.us/chart/<md5>` is a page of the current version group; a chart re-uploaded with new audio has a new `md5` and the registry's old one may 404 on files.enchor.us while the chart page still resolves through `versionGroupId`. `--recheck-all` once a quarter is enough; a dead link is a nuisance, not a wrong answer.
- Hand edits to the registry are data, not code: `overlay.js` validates both values against their character classes before building an href, and `links.published()` drops anything that fails the same check, so a bad edit costs a link, never a redirect.
- The about page's "nothing can be downloaded from it" stays true: the site links out, hosts nothing, and the sentence added says so; the anchor label names the destination rather than an action for the same reason. Keep the independence wording; Chorus Encore and Clone Hero are named as destinations, not partners.
- `openGraph()` must never cache the heading string again. The anchors depend on `state.links`, which can arrive before or after the PNG; `head` as a function and the `.mhead`-only replacement are what keeps the anchors from vanishing on a cold open, and section 06's rewrite of `openGraph` must keep both.
- `python tools/x.py` puts `tools/` at `sys.path[0]`; the `sys.path.insert` line at the top of each tool is what makes `import config` work. Section 09's `tools/ingest_pack.py` imports `config` too and needs the same line.
