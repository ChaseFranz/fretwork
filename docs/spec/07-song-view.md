# 07. Per-song view

**Status:** Ready after 05

**Effort:** M, dominated by the overlay rules (two dialogs that can now stack, a third that shares their trap, Escape closing one layer at a time) and the page suite that proves them, not by the grid, which is one function over rows the page already holds.

**Depends on:** 05 (data-model-v2: `SongKey` in every row, `SHEETS`, `SHEET_OF_CODE`, `loadSheet`, `state.data`, the bundler). Step 6 and the suite bullets under Verification need 04 (the `tests/` tree); until 04 lands, the manual checks in steps 1 to 5 are the gate. Benefits from 02 (a `Pct` column to show per cell), 06 (the client renderer behind a cell click, and the compare view), 03 (an `Added` date on the meta line).

## Goal

One panel that shows every chart of a song at once: title, artist, charter, release, Official or Custom, the date its pack was added when section 03 has recorded one, then a grid of instruments by levels with `D` and `Pct` in each cell and the Expert-anchored tier beside each instrument. A cell opens that chart's graph; the panel opens from a graph's heading, from a small control on a title cell, or from the URL `?song=<SongKey>`, which is shareable. Other folders carrying the same charts are listed as "also in". Nothing changes on the server beyond eight strings in `labels.UI`.

## Why

- The table is one row per chart, so "how hard is this song on bass, and is Hard much easier than Expert" is today three sheet switches and a search. The rows exist on the client already; the page just never groups them.
- 1,758 songs in the newest cache hold 11,904 scored charts: 445 songs have one scored instrument, 1,197 have two, 116 have three, and 229 songs have a single chart. A song's charts are spread over up to three sheets (`Guitar`, `Bass`, `Keys`), and every helper in the page reads only `state.sheet` (`state.js:70-72`), which is why nothing today can show them together.
- A per-song link is the thing people share. `?code=` names one chart; a reader who receives it and wants the Hard chart has no path to it. Title plus artist cannot be the key: 1,853 Expert guitar rows collapse to 1,648 distinct (title, artist) pairs, and section 05 measured 115 title-and-artist groups against 10 content groups. `SongKey` is the key that means "these charts".
- The OG tag question is settled by the hosting: a static site has one `index.html` with one set of tags, so a per-song preview needs per-song HTML. That is a follow-up with a counted cost, not a reason to make the view a route.

## Design

**1. The key is `SongKey`; the folder is the code prefix.** `?song=<SongKey>` (12 lowercase hex, section 05) names the song. Within the rows that share a key, folders are told apart by `Code.slice(0, 8)`, the path hash (`functions/cache.py:61-63`). Because the key hashes every five-fret stream, two folders with one key have identical grids cell for cell, differing only in meta (title, charter, release, Official) and codes. One folder is the *primary*: its meta heads the panel and its codes are what the cells open. Primary is the folder the reader came from (the row's or the graph's code prefix). For a bare `?song=` link, where no folder is named, the comparator is, in order: `Official` true before false; `Release` by `localeCompare`, null last; `Song Title` by `localeCompare`, null last; `Code` prefix ascending. So the same link always shows the same panel, and for the `Sudden Death` pair, where the first two keys tie, the title decides and `Sudden Death` heads the panel. The others are the "also in" list. Rejected: keying the view on a code prefix, because a re-downloaded pack changes every code and the link dies; keying on title and artist, over-merging eleven to one; Code before title as the tiebreak, because it would head that panel with `Sudden Death (Career Version)` for no reason a reader could see.

**2. A panel, not a route.** `#song` is a third fixed dialog built like `#about` (`app.css:113-114`): a card of `min(680px, 100%)`, `.mhead`, a close button. Nothing is added to the site folder, `deploy.BUNDLE_TOP`, `robots.txt` or the 404 page. Rejected: a `/song/<key>` route, which on S3 plus CloudFront means either per-song HTML or a CloudFront Function rewrite that `serve.py` cannot mirror; an inline accordion under the row, because `draw()` rebuilds `#body` as one `innerHTML` string on every keystroke (`table.js:78-80`) and the song's other charts are in other sheets anyway; fetching `song/<key>.json` per song, since after section 05's idle prefetch the rows are already in `state.data` and 1,748 extra files would carry nothing new.

**3. Grid order: instruments down, levels across, Expert first.** Rows are the song's `Type` values in `VALUE_ORDER['Type']` order (`Lead, Co-op, Rhythm, Bass, Keys`; `Drums` joins when section 11 scores it). Columns are `LEVELS` from `boot.js:20`, Expert first, the same left-to-right order as the level chips directly above the table. `VALUE_ORDER['Level']` is Easy-first because it defines an *ascending* order for a sort and a filter list, and a column sorted "ascending" must read Easy, Medium, Hard, Expert (`labels.py:138-144`). The grid is neither a sort nor a filter: it is a fixed row of headings, and it sits on a page whose chips already read Expert, Hard, Medium, Easy, whose default view is Expert, and whose readers look for the hardest chart first. Two orders for the same four words on one screen would be the mistake; the grid follows the chips. Missing cells (instrument present, level absent) are common: 54 partial instruments in multi-chart songs today, 43 of them Rhythm with Expert only, plus three blanks on each of the 229 single-chart songs, 844 cells in all; each shows `MISS_TEXT` with a `title` of `UI.song_no_level` naming the level. A row with one cell and three blanks is the ordinary Rhythm case and is the shape the phone layout is measured on.

**4. Cell content.** Each cell prints `D` with `decimals('D', sheet)` places (2 today) and, when the sheet's manifest `columns` lists `Pct` (section 02), `Pct` beneath it in `--fw-dim`. `Pct` is an integer 0 to 100 (section 02 Design 3), so `decimals('Pct', sheet)` is 0 and the cell prints `98`, never `98.2`. `CalcTier` is Expert-anchored and identical in all four cells of an instrument row by construction (`analyze.py:137-139`), so it is printed once, in the instrument's row heading as `Tier 11` (`UI.song_tier`), rather than four times; a row whose instrument has no Expert chart shows the heading without a tier. This is the one departure from "D, Pct and CalcTier per cell" and the reason is that per cell it is four copies of one number. Rejected: `RemapDiff`, which `DEFAULT_HIDDEN` already judges redundant with `CalcTier` (`labels.py:189-198`).

**5. Stacking, clicks and focus.** `#song` sits at `z-index:1055`, below `#modal` (1060), so a graph opened from a cell draws over the panel and the panel is still there when the graph closes. At most one of `#song` and `#about` is open, since the panel covers the header and its click branch returns for every click. The rules, all in `router.js`:

- *Topmost* is `#modal` if open, else `#song`, else `#about`.
- `onClick` order, top to bottom, each branch returning: `#dd` / `#cd` (untouched); `#how` opens the explainer; `[data-cmp]` (section 06, when present); `[data-song]` (Design 6); **if `graphIsOpen()`**: a backdrop click closes the graph and nothing else (the backdrop test is whichever form is current: "not under `.mhead a`" today, `e.target === el("modal")` after 06), return; **if `songIsOpen()`**: a `.cell[data-code]` opens the graph (`holdRow` is not called, the panel is the opener), `[data-act="close"]` or a target outside `#song .mcard` closes the panel, anything else is swallowed, return; **if `aboutIsOpen()`**: as today (`router.js:31-34`); then chooser, filter, sort, copy pip, row as today. The graph branch moves above the panel and explainer branches because `#modal` is `inset:0` and covers everything when it is open: a branch modelled on the about pattern and placed first would see every graph click as "outside `#song .mcard`" and close the panel under a graph that stays open.
- Escape closes the topmost only (`closeGraph()` if the graph is open, else `closeSong()`, else `closeAbout()`), then returns; the dropdowns still close first as today, and section 06's `state.picking` branch, when present, runs before the dialog branches. Two presses take a reader from a graph over the panel back to the table.
- Tab and Shift+Tab are trapped inside the topmost dialog by `trapTab(dialog, e)`: it lists the focusables under `dialog` matching `FOCUSABLE = 'a[href], button:not([disabled]), input:not([disabled]), [tabindex]:not([tabindex="-1"])'` with `offsetParent !== null`, always calls `preventDefault()`, and moves focus to the next or previous item, wrapping at the ends; with no focusables it only prevents. **One implementation, in `router.js`, with that selector**: if section 06 has landed, it already exists (06 Design 7, its `router.js` entry) and this section calls it for `#song` too; otherwise this section defines it and 06 reuses it. It replaces the bare `preventDefault()` at `router.js:94` for all three dialogs, which makes the report link and the song link in a graph heading reachable by keyboard (06 step 3 claims the same for its controls; whichever lands first gets the credit). `keys.js`'s existing assertion, that Tab is `defaultPrevented` while the graph is open, still holds.
- Focus return: `openSong` records its own `songOpener = document.activeElement`; `openGraph` records `opener` as today, which is the cell when opened from the panel. So closing the graph puts focus on the cell it came from. Closing the panel puts focus on `songOpener` when it is still connected: the table row that held the pip (a `tr` with `tabindex="-1"` takes focus on click), or the row the graph came from when the panel was opened from a graph heading (Design 6 closes the graph first, and `closeGraph` hands focus to that row, `overlay.js:63`, before `songOpener` is read). The fallback, needed only for a URL open, is `el("body").querySelector('tr[tabindex="0"]')` (the row `holdRow` marked, `router.js:64-68`), else nothing. On open, focus goes to the `.here` cell when there is one, else to the panel itself (`tabindex="-1"`, as `#about`), and `#song:focus-visible { outline:none }` keeps the ring off the backdrop as `#modal`'s rule does. The fill never moves focus while `graphIsOpen()` is true.

**6. Two ways in, and both are the same attribute.** `[data-song="<key>"]` is the one hook. Its `onClick` branch precedes the dialog branches: it calls `preventDefault()`, closes the graph if `graphIsOpen()`, then `openSong(key, {from: code})` where `code` is the graph's `state.graph` (or the row's code, from the pip). If the panel is already open for the same key (a graph opened from a cell, then its heading link), closing the graph and marking `from`'s cell `.here` is all that happens; the panel is not rebuilt. The attribute appears (a) as a link in the graph heading, `<a class="sng" href="?song=<key>" data-song="<key>">All charts of this song</a>`, a real href so right-click-copy gives a working link; the heading wraps it and the report link in one `<span class="ms-auto lnk">`, and `ms-auto` moves from `.rpt` to that wrapper so two auto margins do not split the free space (section 13's anchors join the same wrapper); and (b) as a pip on the title cell, `<span class="sp" data-song="<key>" title="All charts of this song">&#8862;</span>`, revealed on row hover like the code copy pip (`app.css:98-101`) but positioned out of flow (`td.song { position:relative }`, `.sp { position:absolute; right:2px; top:5px }`) so a title that fills its last line is not pushed onto another. On a touch screen the pip is never revealed, so the heading link is the path every device has: row, graph, all charts. Keyboard users reach the heading link through the trap. Neither appears when the sheet has no `SongKey` column (the two example spreadsheets under `metrics/`). Rejected: a whole-row second click target, which competes with the graph click on a phone; a keyboard letter on the row, which is undiscoverable.

**7. Loading.** `openSong` opens the panel at once with the heading `UI.song_loading`, then `loadAll()` (`load.js`; section 06 defines it as `Promise.all(Object.keys(SHEETS).map(loadSheet))` with per-sheet errors swallowed; if 06 has not landed, this section adds it there and 06 reuses it); when it settles, `chartsOf(key)` scans every loaded sheet and the panel is filled. `openSong` returns the fill promise, and that promise always resolves, so a caller can sequence on it without inheriting a sheet failure. After section 05's idle prefetch this is instant; on a cold `?song=` visit it is the three requests above. A sheet that failed leaves the panel showing `UI.load_failed` with the reload link, the same text as the table. Rejected: opening the panel only after all sheets arrive, because a bare `?song=` link would show the table for a second with no sign that anything is coming.

**8. "Also in".** When more than one folder shares the key, a line under the meta reads `Also in: <Release> (<Charter>)` per other folder, with the folder's title appended when it differs from the primary's (the `Sudden Death (Career Version)` case); `Release` prints as `MISS_TEXT` when null and the parenthetical is omitted when `Charter` is null. Plain text: the grids are identical, so there is nothing to switch to. Section 10's `Copies` column, when present, is not needed here; the panel derives the list from the rows it already has.

**9. Compare hook for section 06.** The panel reserves a per-instrument control, `<button type="button" class="cmp" data-cmp="<code>,<code>,<code>">Compare all levels</button>`, that section 06 renders and handles: its `[data-cmp]` branch splits the list, sets `state.compare = codes.slice(1)` and calls `openGraph(codes[0], codes.slice(1))` (06's signature, `openGraph(code, vs = state.compare)`), with the instrument's charts in Expert-first order, at most three in all (06's cap is two extras), so an instrument with four levels preselects Expert, Hard and Medium and Easy is one click away in the compare picker. This section does not render the button; it leaves the `.cmp` rule in `app.css` and the exact markup here so section 06 adds one line to `song.js` and one branch to `onClick`. A cell click calls `openGraph(code)` as the row click does, so whatever section 06 puts behind `openGraph` (canvas, hover readout) works from the panel unchanged.

**10. What stays out of the URL.** The primary folder is not in the URL (`code` is, when a graph is open, and that names a folder). Column visibility, order and widths stay in `localStorage` (`url.js:1-4`).

Rules: `?song=` alone opens the panel over the default view (the opening filters `Level=Expert`, `Official=true` from `main.js:58-59` stay, as with `?code=` today, because no `f.`/`r.` key is named). `?song=&code=` opens the panel and then the graph over it, primary folder = the code's prefix. `?code=` alone is unchanged. `readUrl()` returns `{code: string|null, song: string|null}` on every path, including the empty-query branch at `url.js:46`; the pattern check runs inside `readUrl`, so a malformed `song` comes back as `null` and never reaches `state.song`. A well-formed key is set on `state.song` before the first `render()`, for the same reason 05 sets `state.graph` there (`draw()` calls `writeUrl()` and would otherwise strip the parameter while the sheets are in flight); when `loadAll()` settles and the key matches no row, the panel shows `UI.song_not_found`, `openSong` resets `state.song = null` and calls `writeUrl()`, so the parameter leaves the URL within 300 ms of that text appearing. `main.js` becomes (replacing 05's block):

```js
const shared = readUrl();                          // {code, song}, both null on a bare visit
if (shared.code) state.graph = shared.code;
if (shared.song) state.song = shared.song;
render();
const panel = shared.song ? openSong(shared.song, { from: shared.code }) : Promise.resolve();
const codeSheet = shared.code ? SHEET_OF_CODE[shared.code.slice(-1).toUpperCase()] : null;
Promise.all([loadSheet(state.sheet),
             codeSheet && codeSheet in SHEETS ? loadSheet(codeSheet) : null,
             panel])
  .then(() => { render(); if (shared.code) openGraph(shared.code); prefetchIdle(); },
        () => { state.loadError = true; render(); });
```

Two things this fixes against 05's block: the graph waits for the panel to fill, so `opener` is the `.here` cell rather than a loading panel and the fill never moves focus under an open graph; and a `?sheet=Guitar&code=<bass code>` link loads Bass before the graph opens, so `findRow` finds the row (05's `readUrl` already picks the code's sheet when no `sheet` is named, so the second `loadSheet` is usually the same in-flight promise). **`format.js`**: `decimals(col, sheet = state.sheet)`. The memo key already contains the sheet, but the body reads the current sheet through `idx()` and `rowsAll()`, so it changes too:

```js
export function decimals(col, sheet = state.sheet) {
  const memo = sheet + "\u0000" + col;
  if (!places.has(memo)) {
    const columns = SHEETS[sheet].columns, rows = (state.data[sheet] || { rows: [] }).rows;
    const i = columns.indexOf(col);
    const n = rows.some(r => typeof r[i] === "number" && !Number.isInteger(r[i])) ? 2 : 0;
    if (!loaded(sheet)) return n;        // 05's rule: no memo while the rows are absent
    places.set(memo, n);
  }
  return places.get(memo);
}
```

## Risks and gotchas

- **The bundler's single scope.** `song.js` cannot declare `opener`, `heading`, `draw`, `render` or any other top-level name already declared in every other module (18 after 05, 19 after 06); section 05's bundler fails publish on the collision with the file and line, which is the intended catch. `trapTab`, `findRow` and `loadAll` are the three names both this section and 06 want: one implementation each, in the module named above, added by whichever lands first.
- **`overlay.js` must not import `song.js`.** The heading emits a `[data-song]` anchor and `router.js` calls `openSong`; a direct call would make `overlay.js <-> song.js` a cycle and fail the bundle.
- **Escape semantics change.** Today one Escape closes everything; after step 2 it closes one layer. The dropdowns (`#dd`, `#cd`) still close on every Escape as they do now, since they are not dialogs.
- **`opener` shared with `openAbout`.** Unchanged, but the panel's own `songOpener` must not reuse it, or closing a graph opened from a cell would hand focus to whatever opened the panel.
- **The heading link is an anchor with a real href.** The `[data-song]` branch must `preventDefault()`, or the browser navigates to `?song=` and reloads the page; the row branch below it must not run either, which the early `return` ensures. The backdrop test, whichever form it has (`.mhead a` today, `e.target === el("modal")` after 06), never fires on the heading link.
- **Click order is load-bearing.** The `graphIsOpen()` branch must precede the `songIsOpen()` branch; the reverse closes the panel under an open graph (Design 5).
- **`findRow` reads other sheets.** A code whose sheet has not loaded yet returns `null` and the heading is blank until it has; `openSong` waits on all sheets so its cells never hit that, and the `main.js` block loads the shared code's sheet before `openGraph(shared.code)`.
- **`SongKey` moves with the parsers.** A change to `parsers/timing.py` changes every key on the next build (section 05's caveat); a `?song=` link shared before such a build then opens `UI.song_not_found`. Section 03's rule covers it: the rebuild gets a hand-written `[[change]]` entry in `packs.toml` saying the song keys moved and older `?song=` links stop resolving.
- **The `Sudden Death` pair shares a Release and a Charter**, so "also in" prints the title when it differs, or the line would read as the same pack twice; and the primary comparator needs the title tiebreak, or the link would head with the Career Version.
- **Two folders, one key, different `Official`** does not occur in the Local library (all ten pairs are official on both sides) but is possible; the comparator (Official first) is deterministic for it.
- **`decimals('D', sheet)`** reads the named sheet's columns and rows, not the current sheet's; the panel prints `D` from up to three sheets and asks with the right sheet each time. Printing `toFixed(2)` unconditionally would also be correct today (`analyze.py:206` rounds `D` to 2 dp) but would drift if that changed.
- **The graph backdrop over the panel** is `.85` black over `.85` black; the panel is legible beneath at a glance but not readable, which is fine, and no lighter backdrop is used because the `#modal` rule is shared with `#about`.
- **`aria-modal="true"` on two open dialogs** is tolerated by screen readers as long as the topmost has focus, which the trap guarantees; the panel's `aria-label` is `UI.song_label + ": " + title`.
- **The leaderboards userscript** (`../fretladder-leaderboards.user.js`, the Tampermonkey prototype kept beside the repo, untracked) inserts a `.flb` box after `#modal .mhead` (`user.js:323-330`) and reads the code from the modal's `aria-label` (`user.js:368-371`). Both survive this section (the aria-label is unchanged, the box is a sibling of `.mhead`), and any anchor it adds joins the Tab trap, which is correct. Its row lookup reads `boot.data` rows, which section 05 already breaks; nothing here is checked against it (section 13 owns the userscript's fate as a follow-up).
- **Section 06's compare limit of three** leaves one level out of a four-level instrument; the button preselects the three hardest and says nothing else. If section 06 later allows four, the `data-cmp` list simply grows; nothing here depends on the count.
