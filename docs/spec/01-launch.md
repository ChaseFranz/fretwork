**Status:** Ready (the community posts themselves are optional follow-ups: they need the user's accounts and the venues' rules)

**Effort:** S, dominated by a morning of checks in a browser and the user's own posting, not by code (one stdlib Python script, one README subsection, one pipeline-test stage)

**Depends on:** none. Section 00 (fixes-first) is not required to announce the site that is already live, but it should land before the first post-launch data update, because `publish.py` today pairs the newest xlsx with a newer cache and only prints a note (`publish.py:35-43`), and the newest Local cache (`caches/Local_cache_09102026-2324.pkl`) has no xlsx yet.

## Goal

Get the site in front of people and make sure what comes back can be heard. Concretely: confirm the live bundle is the one we think it is and tag it; run one repeatable set of checks against `https://fretladder.com` before any post goes out and after every deploy; post to the community venues the user chooses; then watch three things for two weeks (GitHub issues by label, CloudFront requests and bytes against the Free plan allowance, the budget e-mail) and let what arrives decide whether phase 2 (sections 05, 06, 07) starts on schedule or is pulled forward.

## Why

- Nothing outside this machine has seen the site. Fork traffic on 2026-09-11 is 67 views from 2 unique visitors over 14 days (`gh api repos/ChaseFranz/fretwork/traffic/views`), 0 stars, 0 open issues. Every section after this one is a guess about what visitors want until some arrive.
- The upstream half of the announcement is already done. The comment to Staycation44 was posted on PR #6 on 2026-09-08 at 03:38Z, and the reply at 04:14Z said the attribution and disclaimers are plenty, that the engine is meant to be built upon, and "Fine to share around/comment on the video." It also gave notice that the main formula may change (very short hard songs overvalued, long songs a little undervalued) and that vocals and drums are in progress. The user answered with a thank-you at 04:34Z saying the site will stay a simple online lookup table while the engine is changing. That reply is the permission the community posts and the YouTube comment were waiting on, and the thread is complete: nothing further is posted there.
- The site is hosted on CloudFront's Free flat-rate plan: 1,000,000 requests and 100 GB a month, no overage charges, a spike up to about 3x absorbed, sustained excess over two to three months met by AWS shaping delivery rather than billing. A cold page view is 21 requests plus one per graph opened; at three graphs a visit that is 24 requests and about 900 KB, so the plan is about 41,600 such visits a month (1,000,000 / 24) and about 37 GB, and requests bind first. The thing that would tell us we are near the ceiling is CloudWatch, not an invoice. The $50 budget covers everything the plan does not (S3, Route 53, a plan change).
- The three inbound channels already exist (two issue forms and blank issues) but nothing says who reads them, how often, or what a report turns into. Two weeks of unread rating reports is worse than none.

## Design

1. **The upstream announcement is done; do not repeat it.** The PR #6 thread already holds the ask (03:38Z), the yes (04:14Z) and the acknowledgement (04:34Z). Nothing is owed on the thread. The fork's own rule (CLAUDE.md, "Working with the repo") still applies and is not a promise made there: parser or formula bugs go back upstream as PRs from a branch off `upstream/main`. Rejected: a fourth comment when the community posts go out; it would be noise on a closed PR.

2. **One script for the live checks, run before every announcement and after every deploy.** `tools/check_site.py [BASE_URL]` does with `urllib.request` what README step 7 does by hand, plus the checks listed under Data and interfaces; it runs every check, prints one line each, and exits with the number of failures. It is stdlib Python with no repo import, like `tools/sanitize_songs.py`, so it runs on every platform README section 7 already addresses (the Windows activation line is `README.md:223`) and section 04 can unit-test its parsing. It reads the asset names, the `og:image` path and the code it uses for the shared-link check out of the fetched page, so it never spells a file name that section 05 renames or a code the fixture library lacks. With `--site DIR` it also proves the page that is live is the page that was just published, which the plain status-and-grep step could not. Rejected: a shell script over curl, grep and sed, because it does not run on Windows and cannot be imported by a test; folding it into `deploy.verify()`, which asks S3 (`head-object`) rather than the CDN and cannot see the 404 mapping, the strapline or the brotli encoding.

3. **The browser checks stay manual.** Two things a script cannot prove: that a shared `?code=` link opens the graph with a filled heading (JS), and that the two issue forms open with fields pre-filled (needs a GitHub login). Both are one-minute checks and both are listed in the README subsection with the exact URLs. Section 04's `launch.js` (its Appendix B) asserts the report link's `href` and the graph open; it cannot assert GitHub's side.

4. **Tag what is live.** The tag marks the commit whose `web/static`, `labels.py` and `config.py` produced the live bundle, which a `--no-publish` deploy must prove with the diff in Current state; the message records the bundle's publish time and the strapline, as `v1.0.0` did. Rule from CLAUDE.md: every release of the hosted site gets a `fretladder-vX.Y.Z` tag, never one of upstream's `vX.Y`. The strapline counts rows, one per chart a reader can open, and keeps counting rows when section 10 adds `Copies`; check 1's regex is the contract. Rejected: tagging retroactively at a guessed commit.

5. **Fix the fork's About before posting.** `gh repo edit ChaseFranz/fretwork --description "Fretladder: calculated difficulty ratings for Guitar Hero, Rock Band and Clone Hero charts, on a fork of Staycation44's fretwork engine" --homepage https://fretladder.com`. No commit; it is repository metadata.

6. **Community posts are the user's act, and the venues' rules are not known here.** The section supplies a short factual template and the three answers visitors will ask for (official? downloads? why is X rated Y?) and lists the venues as optional follow-ups: Clone Hero Discord, r/CloneHero, the YARG Discord (the posted comment named CH/YARG users), the Chorus Encore (Enchor) community, and a comment on the explainer video, which Staycation44 approved in so many words. Order: the YouTube comment first, because it is the one venue with explicit permission and the video is where the site's readers already are; then one Discord or subreddit; then wait a week before the next, so the feedback of each post is distinguishable. Rejected: posting everywhere the same day, because a spike from four venues at once is the one traffic shape the Free plan does not absorb, and because a problem found by the first post would be repeated to the other three.

7. **Watch three things, weekly, for two weeks.** Issues by label (`song pack`, `rating`, `accessibility`, and unlabelled), CloudFront `Requests` and `BytesDownloaded` per day from CloudWatch against 1,000,000 and 100 GB a month, and the budget e-mails. The commands go in README section 7 as a new subsection "After it is live", beside the fix table, because that file is the runbook. Thresholds: 700,000 requests in any 30-day window, or a day over 35,000 requests (a 30-day pace past the allowance), means section 05 moves to the front of the queue; a budget e-mail at any threshold means read the Cost Explorer breakdown before anything else, because the plan itself cannot bill.

8. **Phase 2 waits.** Sections 05, 06 and 07 start two weeks after the last community post, or when the library passes about 20,000 charts, whichever is first. A rating report does not move the date; it is triaged as Design 9 says. The size number comes from the measured page: 150 bytes a row raw and about 25 bytes brotli, so 20k charts is a 3.0 MB page, 510 KB compressed, and the Guitar sheet alone would be around 11,000 rows against the 71 ms measured for painting 6,610, which is where the first paint and every filter change become visible on a phone.

9. **What each channel yields is written down.** A `song pack` issue is an entry for section 03's `packs.toml` and a job for section 09's ingest tool; until those exist it is triaged by hand (is the pack public, is it already in the Source column, what size) and answered with the batch policy the form states. A `rating` issue is calibration evidence: if it describes flow (strum, HOPO, anchoring) it is the known gap the explainer names (`functions/labels.py:218-222`, "What it does not know") and gets a link to that section; if it describes a density or length effect it is forwarded to upstream's tracker with the code, because the formula is theirs and Staycation44 has said a change is coming; either way it is left open on the fork until the chart's number moves or the explainer covers it. A blank issue is a bug or an accessibility report; labelling happens at triage, so `no:label` is the inbox and `accessibility` is what a triaged report becomes. Section 02's percentile column is the planned answer to the largest expected class of rating reports ("412 means what?"), which is why it is the first code section after this one.

## Data and interfaces

**`tools/check_site.py [BASE_URL] [--site DIR | --strapline TEXT]`** (new; `BASE_URL` defaults to `https://fretladder.com`, trailing slash stripped). Stdlib only: `argparse`, `re`, `secrets`, `sys`, `time`, `urllib.request`, `urllib.error`; it imports nothing from the repo. `fetch(url, headers={}) -> (status, headers, body)` catches `HTTPError` and returns its code, headers and body; `HTTPError` and `URLError` after a 15 s timeout count as a failed check, never a traceback. Prints one line per check, `ok   #N name`, `skip #N name (reason)` or `FAIL #N name: what was found`, then `10 checks: A ok, B skip, C failed`, and exits with `C`. Skips are not failures. Local mode is `BASE_URL` starting `http://`: a plain file server (`python -m http.server`) neither compresses nor maps a 404 to our page nor carries the fixture's social-preview PNG, so the checks marked below print `skip` there instead of `FAIL`. Checks, in order:

| # | Request | Passes when |
|---|---|---|
| 1 | `GET /`, no `Accept-Encoding`, so the body is plain | 200, `content-type` starts `text/html`, body matches `Updated [0-9]+ [A-Z][a-z]+ [0-9]{4}  -  [0-9,]+ charts`; with `--strapline TEXT` the body must also contain `TEXT`, and with `--site DIR` it must contain the strapline read from `DIR/index.html` with the same regex; on a mismatch the line prints the strapline it found |
| 2 | `GET /` with `Accept-Encoding: br, gzip`; header read only, body discarded, nothing decompressed | `content-encoding` is `br` or `gzip`; retried once after 2 s, because CloudFront can serve the first request after an invalidation uncompressed; `skip` under `http://` |
| 3 | the check 1 body | contains `id="fw-boot"` and `property="og:image"`; captures the `content` of the `og:image` meta and strips the origin to a path (`graph/10145439XG.png` today); captures the `src` of the one `<script type="module">` and the `href` of every `<link rel="stylesheet">` |
| 4 | `GET /about.html` | 200, `text/html`, body has no `<script` and at least one `<h2`; under `https://` also contains `<link rel="canonical" href="<BASE_URL>/about.html">` |
| 5 | `GET /robots.txt` | 200, body contains `Disallow: /graph/` and `Allow: /<og path>` |
| 6 | `GET /<og path>` | 200, `content-type: image/png`; under `http://` a 404 prints `skip` (a fixture publish has no such chart) and a 200 must still be `image/png` |
| 7 | `GET /<module src>` | 200, `content-type` starts `text/javascript` or `application/javascript` (the `binary/octet-stream` failure, `README.md:317`; S3 must answer `text/javascript`, which `deploy.verify()` asserts, and Python before 3.12 answers `application/javascript` locally) |
| 8 | `GET /<href>` for every stylesheet link | 200, `content-type` starts `text/css`; one line covers all of them and names the first that fails |
| 9 | `GET /no-such-page-<8 hex>` | status 404; under `https://` the body must contain `class="code">404<` (the marker in `web/static/404.html`, chosen over the prose in `labels.UI` so a wording edit cannot break the script); under `http://` the status alone passes and the line says `(status only)` |
| 10 | `GET /?code=<og code>` where the code is the og path's stem | 200 (the shared-link form; the JS side is the browser check) |

If check 3 finds no `og:image` (a `serve.py` page, which is built with `public=False`), checks 5, 6 and 10 print `FAIL ... no og:image path`; the script is for publish output. The strapline regex is the one README step 7 greps (`README.md:300`), with the date shape pinned. Expected results: against `https://fretladder.com`, ten `ok`; against `python -m http.server 8000 --directory site/Local`, nine `ok` and one `skip` (check 2); against section 04's fixture publish, eight `ok` and two `skip` (checks 2 and 6). Against `https://example.com`, `FAIL` on check 1 and on every check that needs the page, exit 9 or more.

## Risks and gotchas

- The transcript and the earlier planning notes say the PR #6 comment is "prepared, not posted". It was posted on 2026-09-08 at 03:38Z, with two phrases changed by the user ("CH/YARG", "keep it private or take it offline"), answered at 04:14Z, and acknowledged at 04:34Z. A session that trusts the notes will post it twice; the `gh api` command under Launch comment record is the check.
- The manifest predates `69b5a8f`, so the next `publish.py` or bare `deploy.py` re-renders all 11,904 PNGs (about 24 minutes at 0.12 s each). `write_if_changed` keeps bytes and mtimes when matplotlib produces the same PNG, so the sync should upload nothing, but a session expecting "zero graphs rendered" (section 02 step 5 says so) or running a bare `deploy.py` in the hour before a post will wait half an hour. Run that publish once, deliberately, before section 02. Until section 00 lands, run `deploy.py` only with `--no-publish`: a bare run pairs the 2031 spreadsheet with the 2324 cache and the `Note:` it prints is the only warning (harmless today: the review measured identical five-fret note streams for all 11,904 codes in both caches; after section 00 the same run refuses and needs `analyze.py` first).
- The `aws` login token expires between sessions and the failure mode is a deploy that hangs on the first `s3 sync` with a `Please reauthenticate` line buried in the output. Log in before every deploy, and never leave `deploy.py` running unattended across a session boundary.
- `--dry-run` is not offline: it lists the bucket and needs the same login. Section 04 introduces an offline `deploy.plan()` for CI; until then CI cannot exercise deploy.
- Requests count whether or not the response is a 304. Because the page and modules are `no-cache`, a returning visitor costs the same 21 requests as a new one; the Free plan measures requests, not bytes, and this is why section 05's hashed immutable assets are the real fix and why 700,000 in a month is the trigger.
- The plan absorbs a short spike but a launch that lands on the front page of a large subreddit is not a short spike. The mitigation is Design 6's one-venue-at-a-time rule, not a larger plan; a plan upgrade is a paid, monthly commitment and the budget e-mail would be the first sign it is wanted.
- Anonymous visitors cannot file: both forms redirect to GitHub login. Expect rating disagreements to arrive as replies under the post instead. Copy the ones with a code into issues by hand so the record is in one place; do not add an e-mail address to the site for this.
- Discord caches link previews. Changing `page.OG_IMAGE` (`web/page.py:20`) after a post does not change what the post shows.
- Upstream's formula change will move numbers (Staycation44 on PR #6: short hard songs down, long songs up). The footer's beta note already says numbers can move between updates (`functions/labels.py:293`); do not claim stability in a post, and when the change is merged record it in section 03's changelog rather than announcing a "new formula".
- The fork's issue labels are GitHub's nine defaults plus `song pack`, `rating` and a custom `accessibility`; a report filed as a blank issue arrives unlabelled, which is why the watch block searches `no:label` as well as the three labels.
- `origin/screenshots` must stay: the four images in the PR #6 body resolve through it and the thread is the launch record (section 00, Design (g)); no further comment is planned there, so section 00's "plans to comment" reason is now "the thread is the record".
- `gh` on this box lacks the `notifications` scope, so the watch state cannot be scripted; the web UI is the check. Do not run `gh auth refresh` from a script.
- Check 2 can fail once right after a deploy: CloudFront may serve the first request after an invalidation uncompressed. The script retries once after 2 s; a second failure is real.
- The `songs/` library on this box is 197 MB after sanitising (it was tens of gigabytes with audio); the pipeline never reads audio, so keep `tools/sanitize_songs.py` in the loop before any pack that arrives through the request form is built (`README.md:228`).
